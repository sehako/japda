# Google 소셜 로그인과 인증 기반

## 목적과 성공 기준

웹 SPA 사용자가 백엔드 주도의 Google 로그인으로 서비스 사용자를 생성하거나 재인증하고, 서비스가 발급한 JWT 쿠키로 자신의 인증 상태와 현재 역할을 확인할 수 있게 한다. 첫 로그인 사용자는 `BUYER` 역할을 갖는다. 설정된 `@gmail.com` 계정은 Google 로그인 시 `ADMIN` 역할을 부여받으며, 변경된 설정이 애플리케이션에 반영된 뒤 목록에서 제외되면 다음 관리자 요청부터 권한을 잃는다.

이 기능은 인증과 역할 저장의 기반을 제공한다. 기존 도메인 API의 `X-Buyer-Id`·`X-Seller-Id` 헤더를 인증 사용자 ID로 교체하거나 해당 API에 역할별 접근 규칙을 적용하는 작업은 포함하지 않는다.

## 현황과 범위

백엔드에는 사용자 테이블과 Spring Security 설정이 없다. 상품·판매·주문·결제·배송지 API는 요청자가 지정한 구매자 또는 판매자 숫자 ID를 사용하며, 이 ID를 서비스 사용자와 연결하는 제약이 없다. 현재 웹 SPA가 이번 인증 기능의 유일한 클라이언트다.

이번 범위에는 Google OIDC 로그인, 사용자·다중 역할 저장, 관리자 설정 정책, 서비스 JWT의 발급·검증, 쿠키 및 CSRF 보호, 인증 상태 조회와 로그아웃, 인증 오류 응답이 포함된다. Google 외 로그인 수단, 갱신 토큰, 판매자 신청·관리자 승인 흐름, 기존 도메인 데이터의 소유자 연결, 기존 API의 헤더 교체와 접근 제어는 후속 작업으로 남긴다. 후속 판매자 활성화는 관리자 승인 후 `SELLER`를 부여하는 방식으로 설계한다.

## 사용자와 역할

- 서비스 사용자에게 내부 숫자 ID를 부여한다. Google 계정은 `provider=GOOGLE`과 Google OIDC의 `sub`로 식별하며, 이 조합에 고유 제약을 둔다. 이메일은 변경될 수 있으므로 사용자 식별 키나 고유 제약으로 사용하지 않는다.
- 로그인할 때 Google이 제공한 이메일과 검증 상태를 갱신한다. 검증된 이메일이 없는 계정은 로그인시키지 않는다. 처음 생성된 사용자에게 `BUYER`를 부여한다.
- 역할은 사용자와 별도 테이블에 저장해 한 사용자가 `BUYER`, `SELLER`, `ADMIN`을 함께 가질 수 있게 한다. 사용자·역할 조합에는 중복 방지 제약을 둔다.
- 관리자 허용 목록은 애플리케이션 설정으로 주입하고 `@gmail.com` 주소만 허용한다. 설정값은 애플리케이션 시작 시 로드되며, 변경 적용에는 설정을 반영한 재시작 또는 재배포가 필요하다.
- Google 로그인 시 검증된 이메일이 허용 목록에 있으면 저장된 `ADMIN` 역할을 부여하고, 없으면 저장된 `ADMIN` 역할을 제거한다. 목록에 새로 추가된 사용자는 다음 Google 로그인부터 승격된다.
- 관리자 권한을 사용할 때는 저장된 `ADMIN` 역할과 현재 애플리케이션 설정의 이메일 허용 여부를 모두 확인한다. 변경된 설정이 적용된 뒤 목록에서 제거된 계정은 DB의 역할 갱신을 기다리지 않고 다음 관리자 요청부터 거부한다. 인증 상태 조회도 이 유효 역할 집합을 반환한다.

`users` 테이블은 다음 컬럼으로 구성한다. 기존 테이블과 같은 PostgreSQL ID 및 시간 타입을 사용한다.

| 컬럼 | 타입 | 제약과 용도 |
| --- | --- | --- |
| `id` | `BIGINT` | `GENERATED BY DEFAULT AS IDENTITY` 기본 키. 서비스 내부 사용자 ID |
| `provider` | `VARCHAR(20)` | `NOT NULL`. 이번 범위에서는 `GOOGLE`만 허용 |
| `provider_subject` | `VARCHAR(255)` | `NOT NULL`. Google OIDC `sub` 원문 |
| `email` | `VARCHAR(320)` | `NOT NULL`. 최근 성공한 Google 로그인에서 확인한 이메일. 고유 제약 없음 |
| `email_verified` | `BOOLEAN` | `NOT NULL`. 최근 성공한 로그인에서 확인한 Google 이메일 검증 상태 |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | `NOT NULL`. 사용자 최초 생성 시각 |

`users(provider, provider_subject)`에 고유 제약을 둔다. 검증되지 않은 이메일은 사용자 정보를 쓰기 전에 거부하므로 정상 저장된 `email_verified` 값은 `true`다. 이메일은 Google이 제공한 값을 저장하고, 관리자 `@gmail.com` 허용 목록과 비교할 때만 대소문자를 구분하지 않는다. Google `sub`는 변형하지 않는다. 로그인 때 이메일과 `email_verified`를 갱신하고 `created_at`은 유지한다. 서비스 닉네임은 추후 프로필·온보딩 스펙에서 입력·중복·변경 규칙을 정하며, 이번 `users` 테이블에 `nickname` 컬럼을 두지 않는다. Google 표시 이름·프로필 사진·전화번호도 이번 인증 흐름에 필요하지 않아 저장하지 않는다.

`user_roles` 테이블은 `user_id BIGINT NOT NULL`과 `role VARCHAR(20) NOT NULL`로 구성한다. `user_id`는 `users(id)`를 참조하고, `(user_id, role)`을 기본 키로 사용한다. `role`은 `BUYER`, `SELLER`, `ADMIN`만 허용한다. 이번 범위에서는 기존 상품·주문 등의 구매자·판매자 ID에 `users` FK를 추가하지 않는다.

## 로그인과 JWT 흐름

1. SPA가 `window.location.href`로 백엔드의 `/oauth2/authorization/google`에 이동한다.
2. 백엔드는 Spring Security OAuth2 Login의 authorization code 흐름을 사용한다. Google 왕복 중에는 `state` 검증을 위한 임시 세션을 사용한다.
3. Google 콜백 `/login/oauth2/code/google`에서 인증된 OIDC 정보를 받아 `sub` 기준으로 사용자를 생성·갱신하고 역할을 동기화한다.
4. 백엔드는 내부 사용자 ID를 `sub`로 담은 서비스 JWT를 발급한다. JWT에는 역할을 담지 않는다. 서명 키는 환경 설정으로 공급하며 코드·문서·저장소에 실제 값을 넣지 않는다. 발급자, 대상, 발급·만료 시각을 검증하고 유효기간은 1시간으로 둔다.
5. 백엔드는 JWT를 `HttpOnly` 쿠키에 설정한 뒤, 서버 설정에 고정된 SPA 성공 주소로 리다이렉트한다. JWT 또는 Google 토큰을 URL에 넣지 않는다. SPA에서 임의의 리다이렉트 주소를 요청받지 않는다.
6. SPA는 자격 증명을 포함해 인증 API를 호출한다. 백엔드는 JWT의 내부 사용자 ID로 현재 사용자와 역할을 DB에서 조회한다. 토큰 만료 시 갱신 토큰 없이 Google 로그인으로 다시 이동한다.

Google OAuth 임시 세션과 이후의 JWT 쿠키 인증은 책임을 분리한다. JWT 인증 API는 OAuth 세션을 사용자 인증의 근거로 삼지 않는다.

## 쿠키·CSRF·HTTP 계약

- 운영 환경에서 JWT 쿠키는 `HttpOnly`, `Secure`, `SameSite=Lax`로 설정한다. 쿠키 경로는 `/api`로 제한하고 유효기간을 JWT의 1시간 만료와 맞춘다. 로컬 HTTP 개발 환경의 `Secure` 설정은 별도로 구성한다. `SameSite=Lax`가 성립하는 동일 사이트의 SPA·API 배치를 전제로 하며, 다른 사이트 배치는 쿠키 정책을 다시 결정해야 한다.
- 허용된 SPA 출처만 명시적으로 CORS 자격 증명 요청을 사용할 수 있다. CSRF 토큰 전달 헤더도 허용한다. CSRF 토큰은 JWT와 별도 쿠키로 관리하고 조회 응답의 토큰을 SPA가 헤더에 담아 보내면 백엔드가 검증한다. 쿠키가 자동 전송되는 상태 변경 요청에는 CSRF 검증을 적용한다.
- `GET /api/auth/me`는 유효한 JWT의 내부 사용자 ID, 이메일, 현재 유효 역할 목록을 반환한다. 인증되지 않았거나 토큰이 만료된 요청은 `401`로 응답한다.
- `GET /api/auth/csrf`는 유효한 JWT를 요구하며, SPA가 이후 상태 변경 요청의 헤더에 실을 CSRF 토큰을 제공한다. CSRF 토큰은 사용자 인증을 대신하지 않는다.
- `POST /api/auth/logout`은 유효한 JWT와 CSRF 토큰을 검증한 뒤 JWT 쿠키를 제거하고 `204`로 응답한다. 만료된 JWT의 쿠키는 브라우저의 쿠키 만료로 제거된다. 서버 측 JWT 폐기 목록은 두지 않으므로 이미 복사된 JWT는 최대 1시간의 원래 만료 시각까지 유효할 수 있다.
- Google 로그인 실패 시 백엔드는 비밀값을 포함하지 않는 오류 코드만 고정된 SPA 실패 주소로 전달한다. 인증 API의 인증 실패는 `401`, 권한 부족과 CSRF 실패는 `403`으로 응답하며 기존 `ProblemDetail` 오류 형식을 따른다. 보안 필터에서 발생한 오류도 같은 응답 형식을 사용한다.

이번 범위에서 JWT 쿠키 인증을 적용하는 대상은 인증 API다. 기존 도메인 API는 현재 헤더 계약과 접근 상태를 유지하며, 인증 기반 도입만으로 보호된 것으로 간주하지 않는다. 향후 도메인 API 전환 시 인증 사용자 ID와 DB 역할 및 자원 소유권을 함께 확인하고, 쿠키를 사용하는 상태 변경 요청에 CSRF 보호를 적용해야 한다.

## 데이터 경계와 후속 작업

새 사용자 ID를 기존 상품·판매·주문·결제·배송지의 구매자·판매자 숫자 ID에 자동 대응시키지 않는다. 기존 행에는 사용자 FK를 추가하지 않으며, 임의의 숫자 일치로 소유권을 부여하지 않는다. 도메인 헤더 교체 스펙에서 기존 데이터의 연결 또는 격리 정책을 먼저 정한다.

판매자 신청·관리자 승인 기능은 별도 스펙으로 작성한다. 그 기능은 승인 후 저장된 `SELLER` 역할을 변경하며, 이번 JWT가 역할을 포함하지 않으므로 다음 인증 요청에서 변경된 역할을 읽을 수 있다.

## 검증

- Google `sub`가 같은 재로그인은 사용자 중복 없이 이메일과 관리자 역할을 갱신하고, 다른 `sub`는 이메일이 같더라도 별도 사용자로 처리하는지 검증한다.
- 첫 로그인 `BUYER` 부여, 다중 역할 저장, 검증되지 않은 이메일 거부, `@gmail.com` 관리자 목록 추가 시 다음 로그인 승격과 목록 제거 시 다음 관리자 요청 차단을 검증한다.
- JWT 서명·발급자·대상·만료 검증, 역할 미포함, 현재 DB 역할 반영, 쿠키 속성, 허용 출처의 자격 증명 CORS, CSRF 실패를 검증한다.
- 인증 상태 조회·로그아웃·인증 오류의 HTTP 계약을 MockMvc와 Spring REST Docs로 검증한다. Google 실계정이나 실제 비밀값 없이 OIDC 콜백을 모의 검증한다.
- 기존 도메인 API의 헤더 계약이 이 작업으로 바뀌지 않았는지 관련 테스트로 확인하고, 백엔드 `build`를 실행한다.

## 아키텍처 결정과 제외 사항

Google OIDC를 외부 신원 확인에 사용하고, 내부 사용자·역할을 DB에 저장하며, 백엔드 서명 JWT와 쿠키로 웹 SPA를 인증하는 방식은 새 아키텍처 결정이다. 구현 전에 `docs/architecture/decisions/README.md` 형식에 따라 ADR로 기록한다. 인증·인가 코드는 백엔드의 도메인·계층 의존성 규칙과 기존 `ProblemDetail` 계약을 따른다.

이번 스펙에는 프런트엔드 화면 구현, Google 외 제공자, 갱신 토큰, 토큰 폐기 목록, 판매자 승인 API, 관리자 업무 API, 기존 도메인 API의 ID 헤더 교체, 기존 데이터 이전을 포함하지 않는다.
