# Google 소셜 로그인과 JWT 발급

## 목적과 성공 기준

웹 SPA 사용자가 백엔드의 Spring Security OAuth2 Login으로 Google 로그인을 완료하면, 백엔드가 서비스 사용자를 DB에 저장하고 서비스 JWT를 발급한다. 처음 생성된 사용자에게 `BUYER` 역할을 부여한다. Google에서 확인된 이메일이 설정된 관리자 이메일이면 사용자 저장 시 `ADMIN` 역할도 추가한다.

이번 단계는 JWT **발급**까지 구현한다. 발급된 JWT로 API 요청을 인증하거나 역할에 따라 접근을 제어하는 기능은 포함하지 않는다.

## 구현 범위

- SPA가 `/oauth2/authorization/google`로 이동하면 Spring Security OAuth2 Login의 authorization code 흐름을 시작한다. Google 왕복 중 `state` 검증에는 임시 세션을 사용한다.
- Google OIDC 콜백 `/login/oauth2/code/google`에서 검증된 `sub`와 이메일을 받는다. 이메일 검증 상태가 `true`가 아니거나 이메일이 없으면 로그인을 실패 처리한다.
- `provider=GOOGLE`과 Google OIDC `sub`로 사용자를 조회하고, 없으면 생성한다. 재로그인 시 이메일을 갱신한다. 이메일은 사용자 식별 키로 사용하지 않는다.
- 처음 생성된 사용자에게 `BUYER` 역할을 저장한다. 검증된 이메일이 애플리케이션 설정의 관리자 이메일 목록에 있으면 `ADMIN` 역할을 중복 없이 저장한다. 관리자 이메일 목록에는 `@gmail.com` 주소만 설정할 수 있으며 비교 시 이메일 대소문자는 구분하지 않는다.
- 로그인 성공 시 내부 사용자 ID를 `sub`로 담은 서비스 JWT를 발급한다. 발급자, 대상, 발급·만료 시각을 포함하고 유효기간은 1시간으로 둔다. JWT에는 역할을 담지 않는다. 서명 키는 환경 설정으로 공급하며 실제 값을 코드·문서·저장소에 넣지 않는다.
- JWT를 `HttpOnly` 쿠키에 설정한 뒤 서버 설정에 고정된 SPA 성공 주소로 리다이렉트한다. JWT와 Google 토큰은 URL에 넣지 않는다. 로그인 실패 시 비밀값을 포함하지 않는 오류 코드만 고정된 SPA 실패 주소로 전달한다.

## 데이터와 쿠키

`users` 테이블에는 내부 숫자 `id`, `provider`, `provider_subject`, `email`, `created_at`을 저장한다. `id`는 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 기본 키이고, `(provider, provider_subject)`에는 고유 제약을 둔다. `email`에는 고유 제약을 두지 않는다. Google `sub`는 변형하지 않는다. 닉네임, 표시 이름, 프로필 사진, 전화번호는 저장하지 않는다.

`user_roles` 테이블에는 `user_id BIGINT NOT NULL`과 `role VARCHAR(20) NOT NULL`을 저장한다. `user_id`는 `users(id)`를 참조하고 `(user_id, role)`을 기본 키로 사용한다. 이번 단계에서 저장하는 역할은 `BUYER`와 `ADMIN`이다. 기존 도메인 데이터의 구매자·판매자 ID와 새 사용자 ID는 연결하지 않는다.

운영 환경의 JWT 쿠키는 `HttpOnly`, `Secure`, `SameSite=Lax`로 설정한다. 쿠키 경로는 `/api`로 제한하고 만료 시간을 JWT의 1시간 만료와 맞춘다. 로컬 HTTP 개발 환경의 `Secure` 설정은 별도로 구성한다. `SameSite=Lax`가 성립하는 동일 사이트의 SPA·API 배치를 전제로 한다.

## 후속 범위

이번 단계에서는 JWT 검증 필터, JWT를 사용한 인증·인가, `GET /api/auth/me`, CSRF 토큰 API, 로그아웃 API, 자격 증명 CORS 계약을 구현하지 않는다. 따라서 발급된 JWT 쿠키가 있어도 이번 단계의 API는 그 JWT를 인증 근거로 사용하지 않는다. Google 로그인에 필요한 임시 세션도 기존 도메인 API의 인증 근거로 사용하지 않으며, 기존 API의 헤더 계약과 접근 상태를 유지한다. JWT를 사용하는 상태 변경 API를 도입할 때 쿠키 기반 인증에 맞는 CSRF 보호를 함께 설계한다.

관리자 이메일 목록 변경 시 기존 `ADMIN` 역할의 회수와 관리자 요청 시점의 권한 확인은 후속 인가 작업에서 정의한다. 그 전에는 저장된 `ADMIN` 역할을 관리자 API 접근 권한으로 사용하지 않는다. 판매자 역할 부여·승인, Google 외 로그인 수단, 갱신 토큰, 기존 도메인 API의 ID 헤더 교체와 소유권 연결도 포함하지 않는다.

## 검증

- Google OIDC 콜백을 모의해 첫 로그인 시 사용자·`BUYER` 역할 생성, 같은 `sub`의 재로그인 시 사용자 중복 방지와 이메일 갱신, 서로 다른 `sub`의 사용자 분리를 확인한다.
- 검증되지 않은 이메일의 로그인 거부와 설정된 관리자 이메일 로그인 시 `ADMIN` 역할 저장 및 중복 방지를 확인한다.
- 발급된 JWT의 서명, `sub`, 발급자, 대상, 발급·만료 시각과 역할 미포함을 확인한다. 성공·실패 리다이렉트와 JWT 쿠키 속성도 확인한다.
- 기존 도메인 API의 헤더 계약이 바뀌지 않았는지 확인하고 백엔드 `build`를 실행한다. Google 실계정이나 실제 비밀값은 사용하지 않는다.

## 아키텍처 결정

Google OIDC를 외부 신원 확인에 사용하고 내부 사용자·역할을 DB에 저장하며, 백엔드가 서명한 JWT를 쿠키로 전달하는 방식은 새 아키텍처 결정이다. 구현 전에 `docs/architecture/decisions/README.md` 형식에 따라 ADR로 기록한다.
