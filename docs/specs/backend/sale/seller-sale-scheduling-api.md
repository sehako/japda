# 판매자 판매 일정 등록 API 설계

## 목적과 완료 조건

판매자가 본인 소유의 `READY` 상품에 판매일, 가격, 수량을 지정하고 판매일별 한정된 자리를 선착순으로 확보하는 API를 제공한다. 이번 기능은 판매 일정 등록 하나로 한정한다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- 유효한 요청은 판매 일정 한 건을 저장하고 `201 Created`로 등록 결과를 반환한다.
- 판매일 전날 09:00 이상, 판매일 당일 00:00 미만에만 등록할 수 있다.
- 동시 요청에서도 판매일별 정원과 판매자별 하루 한 건 제한을 초과하지 않는다.
- 확정된 실패는 판매 일정이나 판매 자리를 남기지 않는다.
- 실제 PostgreSQL에서 동시성과 롤백을 검증하고 Spring REST Docs로 HTTP 계약을 문서화한다.

## 기존 구조와 선행 조건

[상품 기본 정보 등록 설계](../product/seller-product-registration-api.md), [이미지 최초 등록 설계](../product/seller-product-image-registration-api.md), [백엔드 아키텍처](../../../architecture/backend.md), [상품·판매 경계 결정](../../../architecture/decisions/ADR-009-product-and-sale-domain-boundaries.md)을 따른다.

상품 기본 정보 API는 `DRAFT` 상품을 생성한다. 병행 설계 중인 이미지 API는 이미지 등록과 `DRAFT → READY` 전환을 같은 트랜잭션으로 처리한다. 판매 API는 커밋된 `READY`를 전제로 하며 이미지의 개수나 저장소를 직접 검사하지 않는다. 이미지 등록이 아직 완료되지 않아 조회 시 `DRAFT`이면 등록을 거절하며 자동으로 기다리거나 재시도하지 않는다.

실제 통합에는 이미지 기능의 `READY` 상태와 스키마 변경이 필요하다. 이 설계에서 이미지 업로드나 상태 전환을 중복 구현하지 않는다. 판매 일정 등록은 상품 상태를 변경하지 않는다.

## 범위

포함 범위는 `POST /api/sales`, 입력·시간·소유권·준비 상태 검증, 판매일별 정원, 판매자 중복 방지, 영속성과 동시성 제어, 테스트와 API 문서이다.

다음은 제외한다.

- 판매 일정 상세·목록 조회 및 `Location` 헤더
- 판매 일정 수정, 취소, 자리 반환과 재등록
- 판매 상태 조회, 시간에 따른 상태 전환 작업과 품절 처리
- 주문, 구매 가능 여부 판단, 재고 예약·차감
- 실제 판매자 인증·계정 존재 확인
- 멱등 키, 성공 응답 재생과 엄격한 요청 도착 순서 대기열
- 실행 중 설정 갱신, 이미 확정된 판매일의 정원 변경

## 등록 정책

| 항목 | 계약 |
| --- | --- |
| 판매자 | 임시 `X-Seller-Id` 헤더, 양의 `Long` |
| 상품 | 본인 소유이며 등록 검사 시 `READY` |
| 판매일 | `Asia/Seoul` 기준 날짜 |
| 등록 시간 | 판매일 전날 09:00 이상, 당일 00:00 미만 |
| 판매 시간 | 판매일 00:00 이상, 다음 날 00:00 미만 |
| 가격 | 원화 정수, 양의 `Long` 범위 |
| 판매 수량 | 양의 `Int` 범위 |
| 판매자 제한 | `(seller_id, sale_date)`당 최대 한 건 |
| 선착순 | DB에서 자리 확보에 성공한 순서 |

같은 상품을 서로 다른 판매일에 다시 등록할 수 있다. 같은 판매자는 서로 다른 상품을 사용하더라도 같은 판매일에 두 건을 등록할 수 없다. 실패한 요청은 등록 기회와 자리를 소비하지 않는다.

시간 판정에는 주입된 `Clock`을 사용한다. 날짜와 등록·판매 경계 계산에는 명시적으로 `Asia/Seoul`을 사용하고 서버 기본 시간대에 의존하지 않는다. 판매일 행 잠금을 획득한 뒤 현재 시각으로 등록 가능 여부를 판정한다. 잠금을 기다리는 동안 마감 시각이 지나면 거절한다. 커밋 완료 시각 자체를 마감 기준으로 삼지는 않는다.

예를 들어 `2026-09-12` 판매는 한국 시간 `2026-09-11 09:00`부터 `2026-09-12 00:00` 전까지 등록한다. 판매 기간은 한국 시간 `2026-09-12 00:00`부터 `2026-09-13 00:00` 전까지이다.

## 정원 설정

- `sale.daily-capacity`의 기본값은 `20`이며 양의 `Int`만 허용한다. 잘못된 설정이면 애플리케이션 시작을 실패시킨다.
- 설정 변경은 애플리케이션 재시작 시 반영한다.
- 판매일별 첫 등록 성공 트랜잭션이 당시 설정값을 `SaleDay.capacity`로 저장한다.
- 이미 생성된 판매일은 저장된 정원을 사용하며 재시작으로 변경하지 않는다.
- 최초 등록 트랜잭션이 롤백되면 새로 생성한 판매일 행도 롤백된다.
- 오전 9시에 판매일 행을 미리 만드는 예약 작업은 도입하지 않는다.

여러 인스턴스는 동일한 설정으로 운영한다. 설정값이 다른 인스턴스가 일시적으로 공존하면 판매일 행을 처음 생성해 커밋한 요청의 설정값으로 정원이 확정된다. 어느 경우에도 이후 요청은 DB의 확정 정원을 따른다.

## HTTP 계약

### 요청

```http
POST /api/sales
X-Seller-Id: 1
Content-Type: application/json

{
  "productId": 10,
  "saleDate": "2026-09-12",
  "price": 35000,
  "quantity": 100
}
```

네 필드는 모두 필수이며 `null`을 허용하지 않는다. `productId`는 양의 `Long`, `saleDate`는 유효한 `YYYY-MM-DD` 날짜 문자열이다. 숫자 필드는 JSON 정수로 받으며 소수, 문자열과 타입 범위 초과를 거절한다. 시작·종료 시각은 요청으로 받지 않고 서버가 판매일로 계산한다.

`presentation`은 HTTP 형식과 타입을 검사하고, 값의 필수 여부·양수·등록 시간 등 비즈니스 의미는 domain 규칙으로 검증한다. 누락·`null`을 필드별 오류로 처리할 수 있도록 Request와 application Dto의 입력 타입을 구성한다.

### 성공 응답

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "id": 100,
  "productId": 10,
  "sellerId": 1,
  "saleDate": "2026-09-12",
  "price": 35000,
  "quantity": 100,
  "startsAt": "2026-09-11T15:00:00Z",
  "endsAt": "2026-09-12T15:00:00Z",
  "createdAt": "2026-09-11T00:00:01Z"
}
```

시각은 기존 상품 API처럼 UTC `Instant` 형식으로 반환한다. `startsAt`과 `endsAt`은 저장된 판매일에서 계산한다. 조회 URI를 정의하지 않으므로 `Location`은 반환하지 않는다. 상태와 남은 구매 재고는 이번 응답에 포함하지 않는다. 응답은 커밋 성공 이후 반환하며 Entity를 직접 노출하지 않는다.

## 도메인과 계층 책임

`sale` 패키지 안에서 기존 계층 구조를 따른다.

- `presentation`: `SaleController`, `CreateSaleRequest`가 헤더·JSON 처리와 Dto 변환을 담당한다.
- `application`: `SaleService`, `CreateSaleDto`, `SaleResponse`가 상품 확인, 등록 트랜잭션, 저장과 응답 변환을 담당한다.
- `domain`: `Sale`이 판매 조건을, `SaleDay`가 확정 정원과 자리 확보 규칙을 소유한다. 자리 수는 도메인 메서드로만 변경한다. `SaleRepository`, `SaleDayRepository` 인터페이스를 정의한다.
- `infrastructure`: Spring Data JPA와 domain Repository 구현체가 영속성, 최초 판매일 생성 충돌 처리와 행 잠금을 담당한다.
- `exception`: `SaleException`, `SaleErrorCode`가 기존 공통 예외 계약을 따른다.

`SaleService`는 상품 영역의 `ProductRepository`로 상품을 조회한다. 필요한 조회 메서드를 추가하되 병행 이미지 기능에서 추가한 메서드와 목적이 같으면 재사용한다. `Sale` Entity는 상품 Entity나 상품 Repository에 의존하지 않고 `productId`만 보관한다. 상품 상태의 의미는 상품 domain이 소유하고, application이 소유권·준비 상태 확인과 판매 생성을 조율한다.

application은 `JpaRepository`, `EntityManager`, SQL에 직접 의존하지 않는다. 정원 설정은 애플리케이션 경계에서 읽어 새 `SaleDay` 생성에 값으로 전달하며 domain이 Spring 설정에 의존하지 않게 한다. 공통 분산 잠금 모듈이나 별도 기술 dependency는 도입하지 않는다.

## 영속성

새 Flyway migration으로 두 테이블을 추가한다. 기존 migration은 수정하지 않으며 이미지 기능과 migration 번호가 충돌하지 않도록 구현 시점의 저장소를 기준으로 정한다.

### `sale_days`

| 열 | 타입과 제약 |
| --- | --- |
| `sale_date` | `DATE`, 기본 키 |
| `capacity` | `INTEGER`, 필수, 양수 |
| `registered_count` | `INTEGER`, 필수, `0 <= registered_count <= capacity` |

### `sales`

| 열 | 타입과 제약 |
| --- | --- |
| `id` | `BIGINT`, identity, 기본 키 |
| `product_id` | `BIGINT`, 필수, `products.id` 외래 키 |
| `seller_id` | `BIGINT`, 필수, 양수 |
| `sale_date` | `DATE`, 필수, `sale_days.sale_date` 외래 키 |
| `price` | `BIGINT`, 필수, 양수, 원 단위 |
| `quantity` | `INTEGER`, 필수, 양수 |
| `created_at` | `TIMESTAMP WITH TIME ZONE`, 필수, `Instant` 매핑 |

`sales(seller_id, sale_date)`에 이름이 명확한 유일성 제약을 둔다. 판매자 테이블은 도입하지 않는다. 소유권과 `READY` 검증은 application 흐름에서 수행한다. Entity 간 컬렉션이나 양방향 연관관계를 추가하지 않는다.

시작·종료 시각은 고정 정책에 따라 판매일로 계산하므로 중복 저장하지 않는다. 취소 시각, 상태 Enum, 남은 재고와 부분 유일 인덱스를 미리 추가하지 않는다.

## 트랜잭션과 동시성

같은 판매일의 등록은 PostgreSQL 판매일 행 잠금으로 직렬화한다. 한 요청의 처리 순서는 다음과 같다.

1. 요청의 필수값·타입·범위를 검증한다.
2. DB 트랜잭션에서 판매일 행이 없으면 설정 정원과 자리 수 `0`으로 생성한다. 판매일 기본 키의 생성 충돌은 `INSERT ... ON CONFLICT DO NOTHING`과 같은 충돌 무시 방식으로 처리한다. 일반 insert의 유일성 예외를 잡고 실패한 트랜잭션에서 그대로 계속하지 않는다.
3. 해당 판매일 행을 쓰기 잠금으로 조회한다.
4. 잠금 획득 후 `Clock`으로 등록 가능 시간을 검사한다.
5. 상품 존재·소유권·`READY`를 확인하고, 판매자 중복과 잔여 자리를 확인한다.
6. `SaleDay` 도메인 메서드로 한 자리를 확보하고 `Sale`을 저장한다.
7. 자리 수와 판매 일정 생성을 함께 커밋한다.

다른 요청은 잠금 해제 후 최신 자리 수와 판매자 등록 여부를 검사한다. 서로 다른 판매일의 요청은 같은 판매일 행을 두고 경쟁하지 않는다. 상품 조회는 커밋된 상태를 읽으며, 이미지 기능의 상품 상태 전환 트랜잭션과 미커밋 상태를 공유하지 않는다.

검증 오류, 저장 오류와 판매자 유일성 충돌은 전체 트랜잭션을 롤백한다. 자리 수를 먼저 갱신했더라도 별도 보상 트랜잭션 없이 함께 되돌린다. 판매자 유일성 제약 충돌은 실패한 트랜잭션 바깥에서 분류해 `409`로 변환한다. 다른 무결성 오류까지 판매자 중복으로 변환하지 않는다.

행 잠금과 정원은 같은 DB 트랜잭션으로 관리한다. 정원만 조회한 뒤 잠금 없이 insert하는 방식이나 애플리케이션 메모리 잠금은 사용하지 않는다. DB 잠금 획득 순서는 엄격한 요청 도착 순서를 보장하는 계약이 아니다. 별도 큐와 Redis 잠금은 이번 기능에 도입하지 않는다.

## 오류 계약

기존 `application/problem+json`, `ProblemDetail`, `ErrorCategory`와 공통 handler를 재사용한다. 판매 일정 규칙은 `SALE_*` 코드로 표현하고 공통 handler에 판매 오류별 분기를 추가하지 않는다.

| 상황 | HTTP 상태 | 오류 코드 |
| --- | --- | --- |
| 판매자 헤더 누락 | 400 | `COMMON_REQUEST_HEADER_MISSING` |
| 판매자 헤더 형식·타입 범위 오류 | 400 | `COMMON_REQUEST_HEADER_INVALID` |
| JSON 파싱·필드 타입·날짜 형식 오류 | 400 | `COMMON_REQUEST_BODY_MALFORMED` |
| 판매자 ID가 0 이하 | 400 | `SALE_SELLER_ID_INVALID` |
| 상품 ID 누락·null·0 이하 | 400 | `SALE_PRODUCT_ID_INVALID` |
| 판매일 누락·null | 400 | `SALE_DATE_REQUIRED` |
| 가격 누락·null·0 이하 | 400 | `SALE_PRICE_INVALID` |
| 수량 누락·null·0 이하 | 400 | `SALE_QUANTITY_INVALID` |
| 상품 없음 또는 본인 소유가 아님 | 404 | `SALE_PRODUCT_NOT_FOUND` |
| 상품이 `READY`가 아님 | 409 | `SALE_PRODUCT_NOT_READY` |
| 등록 시작 전 또는 마감 이후 | 409 | `SALE_REGISTRATION_CLOSED` |
| 동일 판매자의 같은 판매일 중복 등록 | 409 | `SALE_SELLER_ALREADY_REGISTERED` |
| 판매일 정원 초과 | 409 | `SALE_CAPACITY_EXCEEDED` |
| 예상하지 못한 DB·내부 오류 | 500 | `COMMON_INTERNAL_SERVER_ERROR` |

필드 의미 오류의 논리 속성은 `sellerId`, `productId`, `saleDate`, `price`, `quantity`를 사용한다. 여러 오류가 동시에 존재할 때 모든 오류를 수집하지는 않는다. 내부 SQL이나 예외 메시지를 공개하지 않는다.

승인된 판매 API 계약에서는 다른 판매자의 상품을 없는 상품과 같은 `404`로 처리한다. 이미지 API가 소유자 불일치를 `403`으로 처리하는 것과 다르므로 기존 `PRODUCT_ACCESS_DENIED`의 의미나 HTTP 변환을 바꾸지 않는다.

커밋 성공 후 응답이 유실되면 실제 등록은 남아 있다. 재전송은 등록 가능 시간 안에서도 판매자 중복으로 `409`가 될 수 있으며 최초 성공 응답을 재현하지 않는다. 커밋 결과가 불명확한 장애를 확정된 롤백으로 단정하지 않는다. 이번에는 조회 API도 제공하지 않으므로 클라이언트가 결과를 재조회하는 기능은 후속 범위이다.

## 검증 전략

### 도메인·애플리케이션

- 필수값, 가격·수량·식별자 범위, 양수 경계를 검증한다.
- 주입한 `Clock`으로 등록 시작 직전·정각, 마감 직전·정각을 검증한다.
- 잠금 대기 이후 마감한 요청을 거절하는지 확인한다.
- 상품 없음, 다른 소유자, `DRAFT`를 거절하고 `READY` 상품은 허용한다.
- 판매일로 계산한 UTC 시작·종료 시각을 확인한다.
- 자리 확보 규칙, 설정 기본값과 잘못된 설정의 시작 실패를 검증한다.

### PostgreSQL 영속성·동시성

- Testcontainers로 migration, 필드 매핑, 외래 키, 유일성 및 자리 수 제약을 검증한다.
- 판매일 행이 없는 상태에서 정원보다 많은 서로 다른 판매자의 요청을 동시에 실행해 성공 건수와 DB 자리 수가 정확히 정원인지 확인한다.
- 같은 판매자의 동일·서로 다른 상품 요청을 동시에 실행해 정확히 한 건만 성공하고 한 자리만 소비하는지 확인한다.
- 자리 수 변경 후 저장 실패를 재현해 기존 판매일의 자리 수가 원복되는지 확인한다.
- 최초 등록 실패 시 판매일 행과 판매 일정이 모두 남지 않는지 확인한다.
- 동일 DB에 대해 설정값이 다른 애플리케이션 컨텍스트로 등록해 기존 판매일의 정원 유지와 새 판매일의 변경값 적용을 확인한다. 테스트 시간은 해당 날짜의 등록 가능 시간으로 설정한다.
- 상품·판매일이 다른 등록과 판매자별 다른 판매일 등록을 검증한다.
- 동시성 테스트는 요청마다 독립된 트랜잭션을 사용하고 완료 후 별도 조회로 행 수와 자리 수를 대조한다. 같은 테스트 트랜잭션이나 메모리 대역만으로 잠금 검증을 대체하지 않는다.

### HTTP·문서

- MockMvc로 헤더, JSON 정수 타입, 필수값, 성공 본문, `Location` 부재와 오류 계약을 검증한다.
- 같은 테스트에서 Spring REST Docs로 헤더·요청·응답 필드와 대표 오류를 문서화한다.
- HTTP부터 PostgreSQL 저장까지 통합 검증하고, 관련 테스트와 Gradle `build`로 문서 생성을 확인한다.

테스트 클래스와 메서드는 기존 한글 네이밍과 `@DisplayName` 규칙을 따른다. 문서 작성 단계에서는 구현 테스트를 실행하지 않으며 위 항목은 후속 구현의 완료 기준이다.

## 후속 요구사항

취소 기능에서는 판매 시작 전 취소, 즉시 자리 반환, 취소 이력 보존을 지원한다. 취소한 판매자는 등록 시간 안에서 자리가 남아 있으면 다시 경쟁할 수 있고 우선권은 없다. 그때 판매자별 제한은 취소되지 않은 일정 최대 한 건으로 변경한다.

위 정책은 후속 설계의 입력이며 이번 API에 취소 필드나 로직을 포함하는 근거가 아니다. 취소 기능 구현 시 새 migration으로 취소 필드와 부분 유일 인덱스를 도입하고 중복 취소·자리 반환·재등록의 동시성을 별도로 검증한다.

임시 판매자 ID를 바꿔 제한을 우회하는 문제는 인증 기능에서 해결한다. 현재 API는 실제 판매자 신원을 보장하지 않는다.
