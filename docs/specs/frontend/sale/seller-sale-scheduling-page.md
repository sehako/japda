# 판매자 판매 일정 등록 페이지 설계

## 목적과 완료 조건

판매자가 독립된 페이지에서 본인 소유의 판매 준비 완료 상품을 선택하고 다음 판매일의 가격과 수량을 등록할 수 있게 한다. 기존 백엔드 API를 그대로 연동하며 판매 일정의 조회나 수정 기능은 포함하지 않는다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- `/seller/sales/new`에 직접 접근해 판매 일정 등록 페이지를 볼 수 있다.
- 개발 설정에서 주입한 판매자 식별자로 본인 소유의 `READY` 상품을 기본 최신순으로 조회한다.
- 최신 등록순, 오래된 등록순, 상품명 오름차순과 상품명 내림차순으로 상품을 정렬할 수 있다.
- 상품의 내부 식별자는 화면에 노출하지 않는다.
- 커서가 반환되면 다음 상품 페이지로 이동하고 방문한 이전 페이지로 돌아갈 수 있다.
- 상품, 판매일, 가격과 수량을 입력해 판매 일정 등록 API를 호출한다.
- KST 기준 등록 가능 시간과 판매일을 화면에서 선제 안내하되 서버 판정을 최종 결과로 처리한다.
- 클라이언트 검증과 백엔드 `ProblemDetail` 오류를 필드 또는 폼 수준에 표시한다.
- 제출 중 중복 요청과 입력 변경을 방지한다.
- 모바일과 데스크톱에서 사용할 수 있고 키보드와 보조 기술로 주요 상태와 오류를 인식할 수 있다.
- 한 페이지에 상품 20개가 표시되어도 상품 목록이 화면 전체를 길게 밀어내지 않고 일정 입력과 제출 영역에 접근할 수 있다.
- 프론트엔드 관련 테스트, lint와 build가 통과한다.

## 구현 기준 목업과 선행 계약

프론트엔드는 `apps/frontend`의 Vite, React, TypeScript, TailwindCSS 구성을 사용한다. [프론트엔드 아키텍처](../../../architecture/frontend.md), [프론트엔드 라우팅 결정](../../../architecture/decisions/ADR-012-frontend-routing-with-react-router.md)과 [디자인 지침](../../../DESIGN.md)을 따른다.

[판매자 판매 일정 등록 HTML 목업](../../../mockups/seller-sale-scheduling.html)을 이 화면의 구현 기준 목업으로 사용한다. 구현 결과는 목업의 정보 구조, 문구, 컴포넌트 배치, 여백, 색상, 타이포그래피, 반응형 전환과 상태 표현을 재현해야 한다. 목업의 상품 데이터와 JavaScript 요청 시뮬레이션은 상호작용을 보여 주기 위한 예시이므로 실제 구현에서는 아래 API 계약과 feature 구조를 따른다. 목업과 이 문서의 동작 또는 API 요구사항이 충돌하면 이 문서를 우선한다.

페이지는 다음 백엔드 계약을 사용한다.

- [판매 준비 완료 상품 목록 조회 API](../../backend/product/seller-ready-product-list-api.md): `GET /api/products/ready`
- [판매 일정 등록 API](../../backend/sale/seller-sale-scheduling-api.md): `POST /api/sales`
- [백엔드 API 문서](../../../../apps/backend/src/docs/asciidoc/index.adoc): 실제 HTTP 요청과 응답 예시

`READY`는 판매 일정 등록 준비가 끝난 상품 상태이며 판매 일정이 없는 상품이라는 뜻은 아니다. 목록 API는 판매 일정 존재 여부를 검사하지 않으므로 이미 일정에 사용한 상품도 반환할 수 있다. 반대로 하나의 상품은 서로 다른 판매일에 다시 사용할 수 있다.

판매 일정 등록은 상품이 아니라 `(sellerId, saleDate)`를 기준으로 판매자당 하루 한 건만 허용한다. 프론트엔드는 목록만으로 중복 여부를 추론하지 않고 등록 API의 결과를 처리한다.

## 라우팅

`app` 계층의 route 구성은 다음과 같다.

| 경로 | 동작 |
| --- | --- |
| `/` | `/seller/products/new`로 replace 이동 |
| `/seller/products/new` | 기존 `SellerProductRegistrationPage` 표시 |
| `/seller/sales/new` | `SellerSaleSchedulingPage` 표시 |
| 그 외 | Not Found 페이지 표시 |

`BrowserRouter`를 사용한다. 내부 페이지 이동에는 React Router의 링크를 사용해 전체 문서를 다시 불러오지 않고 브라우저 탐색 기록을 유지한다. 배포 환경에는 애플리케이션 하위 경로를 `index.html`로 전달하는 SPA fallback이 필요하다.

## 페이지와 화면 구성

화면은 seller/admin UI답게 기능 중심으로 구성한다.

1. 상단
   - 서비스 맥락 `JAPDA SELLER`
   - 현재 위치 `판매 일정 등록`
   - 상품 등록 페이지로 이동하는 보조 링크
2. 상품 선택
   - 판매자 본인의 `READY` 상품명
   - 최신 등록순, 오래된 등록순, 상품명 오름차순과 상품명 내림차순을 선택하는 정렬 control
   - `선택`, `상품명` 열로 구성한 표
   - 제한된 높이 안에서 스크롤되는 목록과 스크롤 중 유지되는 표 header
   - 한 번에 한 상품만 선택할 수 있는 체크박스
   - 최초 조회, 빈 목록, 조회 실패와 다음 페이지 조회 상태
   - 방문한 페이지의 cursor와 결과를 보관하는 `이전`·`다음` 커서 페이지네이션
3. 일정 입력
   - 판매일
   - 원화 정수 가격
   - 정수 판매 수량
   - 등록 가능 시간 안내
4. 일정 입력 액션
   - 일정 입력 영역 안의 주요 액션 `판매 일정 등록`
   - 제출 상태 `등록 중...`
5. 완료 상태
   - 상품명, 일정 식별자, 판매일, 가격, 수량과 판매 기간 요약
   - 상품 등록 페이지로 이동하는 보조 링크

```text
┌────────────────────────────────────────┐
│ JAPDA SELLER            판매 일정 등록 │
├────────────────────────────────────────┤
│ 상품 *                    정렬 [최신순] │
│ ┌────┬───────────────────────────────┐ │
│ │선택│ 상품명                        │ │
│ │ ☑ │ 한정판 그래픽 후디             │ │
│ │ ☐ │ 콜라보 레더 스니커즈           │ │
│ └────┴───────────────────────────────┘ │
│ 1페이지 · 20개 상품       [이전] [다음] │
│                                          │
│ 판매일 *                                 │
│ [ 2026-09-11 ]                           │
│ 오늘 09:00부터 24:00 전까지 등록 가능    │
│                                          │
│ 판매 가격 *             판매 수량 *       │
│ [           원 ]        [          개 ]   │
│                                          │
│                       [ 판매 일정 등록 ]  │
└────────────────────────────────────────┘
```

흰 배경, Obsidian 텍스트와 CTA, Concrete Gray 경계선, 사각형 입력을 사용한다. 장식용 accent color, gradient와 shadow는 사용하지 않으며 주요 CTA에만 pill shape을 적용한다. 데스크톱에서는 가격과 수량을 2열로 배치하고 모바일에서는 세로로 쌓는다. 모바일에서는 주요 CTA의 충분한 touch area와 접근성을 유지하되 입력 내용을 가리는 고정 배치는 사용하지 않는다.

상품 표는 데스크톱과 모바일 모두 약 6개 행을 한 번에 확인할 수 있는 최대 높이를 가지며, 상품이 더 많으면 표 내부를 세로로 스크롤한다. 표 header는 상품명을 읽는 맥락이 유지되도록 스크롤 영역 상단에 고정한다. 현재 페이지 상태와 `이전`·`다음`은 스크롤 영역 밖에 둔다. 데스크톱의 일정 입력과 제출 버튼은 상품 행 수와 무관하게 오른쪽 열 상단에서 함께 확인할 수 있게 배치한다. 모바일에서는 상품 목록 다음에 일정 입력이 이어지며, sticky panel이나 화면 고정 CTA는 사용하지 않는다.

등록 가능 상태 안내에는 동일 판매일 중복 등록 제한을 `같은 판매일에는 일정 하나만 등록할 수 있습니다.`로 표시한다. 의미 없이 주의를 반복하는 `주의` prefix는 사용하지 않는다. 이 경고는 제출 버튼의 보조 문구가 아니라 등록 가능 시간 및 판매일 제약과 같은 상태 안내로 취급한다.

## 사용자 입력과 상태

폼 상태와 상품 목록 상태는 `sale-scheduling` feature의 hook에서 구분해 관리한다.

| 상태 | 의미 |
| --- | --- |
| `productPages` | 방문 순서대로 보관한 요청 cursor, READY 상품 목록과 응답 `nextCursor` |
| `currentProductPageIndex` | 현재 표시하는 방문 페이지의 인덱스 |
| `productSort` | 현재 선택한 상품 정렬 방식 |
| `productListStatus` | 최초·다음 페이지 조회의 loading, error와 완료 상태 |
| `selectedProductId` | 선택한 상품의 양의 `Long` 식별자 |
| `selectedProductSummary` | 정렬 또는 페이지 이동 뒤에도 유지할 선택 상품의 식별자와 상품명 |
| `saleDate` | `YYYY-MM-DD` 형식의 판매일 |
| `price` | 원화 가격 입력 원문 |
| `quantity` | 판매 수량 입력 원문 |
| `registrationWindow` | 현재 KST에 따른 등록 가능 여부와 다음 판매일 |
| `submissionStatus` | 입력, 제출과 성공 상태 |
| `fieldErrors` | 필드별 클라이언트 또는 서버 오류 |
| `formError` | 특정 필드에 속하지 않는 화면 수준 오류 |
| `createdSale` | 성공 응답과 선택 당시 상품명으로 구성한 완료 정보 |

상품 목록은 첫 페이지를 `latest`, `size=20`으로 조회한다. 각 페이지는 표 안의 행을 교체해 표시하며 누적 목록으로 확장하지 않는다. 응답에 `nextCursor`가 있을 때만 `다음`을 활성화하고 같은 정렬과 크기로 다음 페이지를 조회한다. 방문한 페이지의 요청 cursor, 결과와 `nextCursor`를 순서대로 보관하며 `이전`은 네트워크 요청 없이 보관한 페이지를 표시한다. 이미 방문한 다음 페이지로 다시 이동할 때도 보관한 결과를 사용한다. 커서는 해석하거나 수정하지 않는다.

정렬 control은 native `select`를 사용하며 `latest`, `oldest`, `name-asc`, `name-desc`를 제공한다. 정렬을 변경하면 진행 중인 상품 목록 요청을 취소하고 선택한 정렬의 첫 페이지를 조회한다. 새 첫 페이지 응답이 성공하면 기존 방문 페이지와 cursor를 폐기하고 새 결과로 교체한다. 정렬별 cursor는 서로 호환되지 않으므로 이전 정렬의 페이지를 재사용하지 않는다. 선택한 상품은 같은 READY 목록 안에서 표시 순서만 바뀌므로 식별자와 상품명을 별도 보관해 정렬 변경 뒤에도 유지하고, 현재 페이지에 보이지 않더라도 선택 상품 요약에서 확인할 수 있게 한다.

정렬 조회가 실패하면 마지막으로 정상 표시한 목록과 선택 상품을 유지하고 select도 마지막으로 적용된 정렬로 되돌린다. 오류와 함께 사용자가 선택했던 정렬로 다시 시도하는 action을 제공한다. 정렬 전환 중에는 페이지 이동과 정렬 control을 비활성화하고 현재 목록 위에 조회 중임을 텍스트로 알리며, 기존 목록을 새 정렬 결과로 오인하지 않게 한다.

목록 API가 전체 상품 수나 임의 페이지로 이동할 cursor를 제공하지 않으므로 전체 페이지 수, 번호별 이동과 마지막 페이지 이동은 표시하지 않는다. 화면의 현재 페이지 번호는 이번 방문에서 첫 페이지부터 순서대로 탐색한 위치만 나타낸다.

각 행은 native checkbox를 제공하지만 선택값은 `selectedProductId` 하나만 관리한다. 체크하지 않은 행을 선택하면 기존 선택을 해제하고 새 상품만 선택한다. 선택한 행을 다시 누르면 선택을 해제한다. 페이지를 이동해도 선택값과 별도 선택 상품 요약을 유지하며, 선택한 상품의 페이지로 돌아오면 해당 체크박스를 checked 상태로 표시한다.

상품 식별자는 API 요청과 클라이언트 내부 상태에 필요하지만 판매자가 일반적으로 확인할 정보가 아니므로 독립된 열이나 상품 요약에 표시하지 않는다. READY 상품 목록 응답은 동명 여부를 제공하지 않으므로 클라이언트는 방문한 상품만 비교해 중복 여부를 추론하거나 별도 표시하지 않는다.

첫 페이지가 빈 배열이면 정상 빈 상태로 표시하고 `상품 등록` 링크를 제공한다. 목록 조회 실패를 빈 목록처럼 표시하지 않는다. `SALE_PRODUCT_NOT_READY` 또는 `SALE_PRODUCT_NOT_FOUND`가 발생하면 현재 선택에 오류를 표시하고 첫 페이지부터 목록을 다시 불러올 수 있는 액션을 제공한다.

## 등록 가능 시간과 판매일

서버의 시간 판정은 `Asia/Seoul` 기준이며 판매일 전날 09:00 이상, 판매일 당일 00:00 미만에만 등록할 수 있다. 따라서 한 시점에 등록 가능한 판매일은 다음과 같다.

| 현재 KST | 등록 가능한 판매일 | 화면 동작 |
| --- | --- | --- |
| 00:00 이상 09:00 미만 | 없음 | 일정 입력과 제출을 비활성화하고 오늘 09:00 시작을 안내 |
| 09:00 이상 다음 날 00:00 미만 | 다음 날 | `saleDate`를 다음 날로 설정하고 `min`, `max`를 같은 날짜로 제한 |

페이지를 계속 열어 둔 상태에서도 09:00과 00:00 경계를 지나면 등록 가능 상태와 날짜를 다시 계산한다. 브라우저 시각 계산은 빠른 사용자 안내일 뿐이며 서버 시계가 최종 기준이다. 시계 차이, 네트워크 지연과 정원 경쟁이 있으므로 제출 직전의 화면 상태와 관계없이 서버 오류를 처리한다.

판매 기간은 서버가 `saleDate`의 KST 00:00부터 다음 날 00:00 전까지로 계산한다. 시작·종료 시각은 입력받지 않는다.

## 클라이언트 검증

서버 요청 전에 다음 항목을 검증한다.

| 입력 | 검증 규칙 |
| --- | --- |
| 상품 | READY 목록에서 선택한 양의 안전 정수 식별자 |
| 판매일 | 현재 클라이언트 KST 기준 등록 가능한 다음 날과 일치하는 `YYYY-MM-DD` |
| 가격 | 공백 없는 십진 정수이며 1 이상 `Number.MAX_SAFE_INTEGER` 이하 |
| 수량 | 공백 없는 십진 정수이며 1 이상 `2,147,483,647` 이하 |

가격과 수량은 입력 중 문자열로 유지하고 검증을 통과한 뒤 숫자로 변환한다. 지수 표기, 부호, 소수, 숫자 사이 공백과 앞뒤 공백을 허용하지 않는다. HTML 입력 속성은 입력 편의를 제공할 뿐이므로 제출 시 같은 규칙을 다시 검증한다.

클라이언트 시각이 서버와 다를 수 있으므로 날짜 검증 통과가 등록 성공을 보장하지 않는다. 상품 소유권, 현재 `READY` 상태, 판매자 중복, 등록 시간과 정원은 서버가 최종 검증한다.

## API 계약과 데이터 흐름

개발용 판매자 식별자와 API 기준 URL은 기존 `shared/config/env.ts` 설정을 재사용한다. `VITE_SELLER_ID`가 없거나 양의 정수가 아니면 API를 호출하지 않고 페이지 수준 설정 오류를 표시한다. 판매자 식별자를 입력하거나 변경하는 UI는 제공하지 않는다.

### READY 상품 목록 조회

첫 페이지:

```http
GET /api/products/ready?sort={latest|oldest|name-asc|name-desc}&size=20
X-Seller-Id: {VITE_SELLER_ID}
```

다음 페이지:

```http
GET /api/products/ready?sort={productSort}&cursor={nextCursor}&size=20
X-Seller-Id: {VITE_SELLER_ID}
```

응답의 `items`는 `{ id, name }` 배열이고 `nextCursor`는 문자열 또는 `null`이어야 한다. API 모듈은 성공 응답의 런타임 형상을 검사하고 계약과 다르면 일반 API 오류로 처리한다.

### 판매 일정 등록

```http
POST /api/sales
X-Seller-Id: {VITE_SELLER_ID}
Content-Type: application/json
```

```json
{
  "productId": 10,
  "saleDate": "2026-09-12",
  "price": 35000,
  "quantity": 100
}
```

성공한 `201 Created` 응답에서 `id`, `productId`, `sellerId`, `saleDate`, `price`, `quantity`, `startsAt`, `endsAt`, `createdAt`을 검증한다. 요청과 응답의 `productId`, `sellerId`, `saleDate`, `price`, `quantity`가 다르면 성공으로 표시하지 않고 계약 오류로 처리한다.

전체 흐름은 다음과 같다.

```text
SellerSaleSchedulingPage / UI
              ↓
useSaleScheduling
              ↓
READY 상품 목록 조회 → 상품 선택과 입력
              ↓
클라이언트 검증
              ↓
createSale API
              ↓
등록 완료 상태 또는 ProblemDetail 오류
```

목록 조회와 등록 요청에 각각 `AbortSignal`을 전달하고 컴포넌트 해제 시 진행 중인 요청을 취소한다. 요청 취소는 사용자 오류로 표시하지 않는다. 등록 성공 뒤 목록을 다시 조회하거나 무효화하지 않고 완료 상태로 전환한다.

## 프론트엔드 구조와 책임

```text
src/
├── App.tsx
├── app/
│   └── router.tsx
├── pages/
│   ├── not-found/
│   │   └── NotFoundPage.tsx
│   ├── seller-product-registration/
│   │   └── SellerProductRegistrationPage.tsx
│   └── seller-sale-scheduling/
│       └── SellerSaleSchedulingPage.tsx
├── features/
│   ├── product-registration/
│   └── sale-scheduling/
│       ├── api/
│       │   └── saleSchedulingApi.ts
│       ├── hook/
│       │   └── useSaleScheduling.ts
│       ├── model/
│       │   └── saleScheduling.ts
│       └── ui/
│           └── SaleSchedulingForm.tsx

    ├── api/

    └── config/
        └── env.ts
```

- `router.tsx`는 route, redirect와 Not Found 연결만 담당한다.
- `SellerSaleSchedulingPage`는 페이지 레이아웃과 판매 일정 feature 조합을 담당한다.
- `SaleSchedulingForm`은 목록·입력·오류·제출과 완료 상태 렌더링을 담당한다.
- `useSaleScheduling`은 목록 페이지네이션, 폼 상태, 시간 경계, 검증과 API 요청 생명주기를 조율한다.
- `saleScheduling` model은 입력 정규화, 검증, KST 등록 가능 시간 계산과 오류 매핑을 담당한다.
- `saleSchedulingApi`는 READY 상품 조회와 판매 일정 등록 HTTP 요청 및 응답 검증을 담당한다.
- 기존 `apiClient`와 `env`는 공통 요청 처리, `ProblemDetail` 변환과 개발 설정 검증에 그대로 사용한다.

UI 컴포넌트에서 API를 직접 호출하지 않는다. 현재의 단순한 조회·생성 흐름과 기존 코드 패턴에 맞춰 React 상태와 `fetch`를 사용한다. 라우팅 외에 새로운 dependency는 추가하지 않는다.

## 오류 처리와 재시도

`apiClient`가 반환하는 `ApiError(status, code, detail, errors)`를 필드 또는 화면 수준 오류로 변환한다. 서버의 `detail`을 사용할 수 있으면 표시하고, 해석할 수 없는 응답이나 네트워크 실패에는 기능별 일반 메시지를 표시한다. 내부 예외, 응답 원문, cursor와 설정값은 화면에 노출하지 않는다.

| 오류 코드 또는 속성 | 표시 위치와 동작 |
| --- | --- |
| `productId`, `SALE_PRODUCT_NOT_FOUND` | 상품 입력 아래, 목록 새로고침 제공 |
| `SALE_PRODUCT_NOT_READY` | 상품 입력 아래, 목록 새로고침 제공 |
| `saleDate`, `SALE_REGISTRATION_CLOSED` | 판매일 아래, 등록 가능 상태 재계산 |
| `SALE_CAPACITY_EXCEEDED` | 판매일 아래 |
| `price`, `SALE_PRICE_INVALID` | 가격 입력 아래 |
| `quantity`, `SALE_QUANTITY_INVALID` | 수량 입력 아래 |
| `sellerId`, 판매자 헤더·설정 오류 | 폼 상단 또는 페이지 수준 오류 |
| `SALE_SELLER_ALREADY_REGISTERED` | 폼 상단, 같은 판매일에는 다시 제출할 수 없음을 안내 |
| 목록의 cursor·sort·size 오류 | 상품 목록 영역, 첫 페이지부터 다시 조회 제공 |
| 네트워크·응답 계약·내부 오류 | 해당 요청 영역의 일반 오류와 재시도 제공 |

목록 최초 조회 실패는 목록 영역에서 재시도한다. 다음 페이지 조회 실패는 현재 페이지와 선택을 유지하고 페이지네이션 영역에서 재시도한다. 등록 실패는 사용자가 수정할 수 있는 입력을 유지한다.

등록 요청의 응답이 유실되면 서버에 일정이 저장됐을 수 있다. 조회 API가 없으므로 네트워크 오류를 확정 실패로 표현하지 않고 `등록 결과를 확인할 수 없습니다. 다시 요청하면 이미 등록된 일정으로 처리될 수 있습니다.`라고 안내한다.

## 제출과 완료 상태

제출 중에는 상품 체크박스, 판매일, 가격, 수량, 페이지 이동과 제출 버튼을 비활성화한다. 중복 submit을 무시하며 `등록 중...`을 `aria-live="polite"`로 알린다.

등록 성공 후 폼 대신 완료 상태를 표시하고 다음 값을 보여준다.

- 선택 당시의 상품명
- 판매 일정 식별자
- 판매일
- 가격과 수량
- 서버가 반환한 판매 시작·종료 시각

판매자 일정 목록이나 상세 API가 없으므로 존재하지 않는 화면으로 이동하지 않는다. 같은 판매자는 같은 판매일에 한 건만 등록할 수 있으므로 `다른 일정 등록` 액션도 제공하지 않는다. 상품 등록 페이지로 이동하는 보조 링크만 제공한다.

## 접근성과 호환성

- 모든 입력에 화면에 보이는 `label` 또는 행의 상품명을 포함한 접근 가능한 이름을 연결한다.
- 필드 안내와 오류는 `aria-describedby`로 입력에 연결한다.
- 필수 필드와 유효하지 않은 필드에 `required`, `aria-invalid`를 적용한다.
- 체크박스 그룹에는 한 상품만 선택할 수 있다는 제약을 접근 가능한 설명으로 제공한다.
- 정렬 control에는 화면에 보이는 label을 연결하고 정렬 변경에 따른 조회 상태와 결과를 `aria-live="polite"`로 알린다.
- 상품 표의 스크롤 영역에는 접근 가능한 이름과 키보드 focus 진입 수단을 제공하되 일반 문서 흐름의 일정 입력 접근을 방해하지 않는다.
- 상품 목록의 loading과 페이지 이동 결과는 `aria-live="polite"`로 알린다.
- 제출과 서버 오류에는 `role="alert"`를 적용한다.
- 오류 발생 시 첫 번째 수정 가능한 오류 필드로 focus를 이동한다. 폼 수준 오류에는 오류 컨테이너로 focus를 이동한다.
- 목록 체크박스, `이전`·`다음`, 입력, 제출과 페이지 링크는 키보드만으로 조작할 수 있어야 한다.
- 상태는 색상만으로 표현하지 않고 텍스트를 함께 제공한다.
- `fetch`, `AbortController`, `Intl.DateTimeFormat`과 React Router가 지원하는 현대 브라우저를 대상으로 한다.
- 프론트엔드와 백엔드 origin이 다르면 백엔드 CORS가 해당 origin과 `X-Seller-Id`를 허용해야 한다. 백엔드 CORS 변경은 이번 범위에 포함하지 않는다.

## 검증 전략

현재의 `node:test` 기반 순수 TypeScript 테스트 관례를 따른다. 라우팅 또는 UI 테스트에 새 테스트 dependency가 꼭 필요해지는 경우 구현 전에 범위를 다시 확인하며, 이번 설계만으로 추가를 확정하지 않는다.

### API와 model 테스트

- READY 상품 첫 페이지와 다음 페이지의 URL, query, 판매자 헤더와 `AbortSignal` 전달을 검증한다.
- 상품 목록의 빈 배열, `nextCursor: null`, 다음 커서와 잘못된 응답 형상을 검증한다.
- 상품 식별자와 상품명 및 `nextCursor`가 실제 백엔드 응답 형상과 일치하는지 검증한다.
- 다음 페이지 조회와 방문 페이지의 이전·다음 이동, 단일 체크, 페이지 이동 후 선택 유지를 검증한다.
- 네 가지 정렬 요청, 정렬 변경 시 진행 요청 취소와 cursor·방문 페이지 초기화, 선택 상품 유지를 검증한다.
- 정렬 변경 조회 실패 시 기존 목록과 선택을 유지하고 새 정렬의 첫 페이지를 재시도하는지 검증한다.
- 판매 일정 등록의 헤더, JSON 본문과 성공 응답 형상 검증을 확인한다.
- 상품·판매일·가격·수량의 정상값과 경계값을 검증한다.
- KST 09:00 직전·정각과 00:00 직전·정각의 등록 가능 상태를 고정 시각으로 검증한다.
- `ProblemDetail` 속성과 오류 코드가 지정한 필드 또는 폼 오류로 변환되는지 검증한다.

### 화면과 route 확인

- `/`, `/seller/products/new`, `/seller/sales/new`와 정의하지 않은 경로의 동작을 확인한다.
- 최초 목록 loading·실패·빈 상태·성공과 다음 페이지 조회 실패·성공 상태를 확인한다.
- 제출 중 입력과 중복 요청이 차단되는지 확인한다.
- 등록 성공 정보와 불명확한 네트워크 오류 안내를 확인한다.
- 모바일과 데스크톱 레이아웃, 키보드 조작, focus 이동과 보조 기술 알림을 확인한다.
- 상품 20개에서 목록 내부 스크롤, 고정 표 header, 일정 입력과 제출 영역 접근성을 확인한다.
- 상품 목록·선택·완료 요약에 내부 상품 ID가 표시되지 않는지 확인한다.
- 배포 환경에서 `/seller/sales/new` 직접 접근과 새로고침이 SPA fallback으로 동작하는지 확인한다.

### 정적 확인

- 프론트엔드 관련 테스트를 실행한다.
- `npm run lint`를 실행한다.
- `npm run build`를 실행한다.

백엔드 계약을 변경하지 않으므로 백엔드 구현과 테스트는 이번 프론트엔드 구현 범위에 포함하지 않는다.

## 주요 결정

- `react-router-dom`과 `BrowserRouter`로 판매자 페이지를 독립 URL에 연결한다.
- 상품 선택에는 기존 `GET /api/products/ready`를 20개 단위로 사용하며 API가 지원하는 네 가지 정렬을 제공한다.
- 정렬 변경 시 cursor와 방문 페이지는 초기화하고 선택 상품은 유지한다.
- 상품 목록 높이를 제한하고 표 내부 스크롤과 고정 header를 사용하며 제출 버튼은 일정 입력 영역 안에 배치한다.
- 상품 ID는 내부 선택과 API 요청에만 사용하고 화면에는 표시하지 않는다.
- READY 목록만으로 일정 등록 여부를 추론하거나 상품을 제외하지 않는다.
- 판매일은 현재 KST에 등록 가능한 다음 날 하나로 제한하되 서버 판정을 최종 기준으로 처리한다.
- 상품 목록과 Form 상태는 구분하지만 현재 범위에는 서버 상태 또는 Form 라이브러리를 도입하지 않는다.
- 다음 페이지 조회 실패 시 현재 페이지와 선택을 유지한다.
- 등록 결과 조회 API가 없으므로 성공 화면은 등록 응답과 선택 당시 상품명을 사용한다.
- 판매자별 하루 한 건 제한 때문에 성공 화면에서 같은 판매일의 추가 등록 액션을 제공하지 않는다.
