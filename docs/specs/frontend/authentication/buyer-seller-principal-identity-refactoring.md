# 구매자·판매자 API의 인증 주체 기반 식별에 맞춘 프론트엔드 전환

## 목적과 완료 조건

백엔드의 [구매자·판매자 API 인증 주체 기반 식별 전환](../../backend/authentication/buyer-seller-principal-identity-refactoring.md)에 맞춰 프론트엔드가 개발용 구매자·판매자 ID를 요청 소유자 정보로 보내는 흐름을 제거한다. 로그인한 사용자의 쿠키 인증으로 보호 API를 호출하고, 변경 요청에는 백엔드가 발급한 CSRF 토큰을 보낸다. 백엔드 전환 명세는 승인된 설계이며, 현재 백엔드 코드에는 보호 API 전환과 `GET /api/auth/csrf`가 아직 구현되지 않았다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- 보호 대상 8개 API에 `X-Buyer-Id`·`X-Seller-Id`를 보내지 않으며, `VITE_BUYER_ID`·`VITE_SELLER_ID` 설정이나 `/api/auth/me`의 `id`·`roles`로 도메인 ID를 추정하지 않는다.
- 보호 요청은 JWT 쿠키를 포함한다. 상태 변경 요청은 `GET /api/auth/csrf`에서 받은 토큰을 응답이 지정한 헤더에 넣는다. 공개 판매 조회는 비로그인으로 계속 사용할 수 있다.
- 구매·판매 화면은 로그인 확인 중, 로그인 필요, 계정 연결 부재, CSRF 오류 및 일반 요청 오류를 구분한다. 판매자 연결 여부를 `BUYER`·`ADMIN` 역할로 추정하지 않는다.
- 토스 결제 성공 복귀에서 인증 만료나 연결 부재로 승인을 진행할 수 없으면 결제 결과를 단정하지 않고 결과 확인 필요로 안내한다. `paymentKey`를 브라우저 저장소에 보관하거나 로그인 뒤 자동으로 승인 요청을 재개하지 않는다.
- 관련 프론트엔드 테스트와 `test`, `build`, `lint`를 통과하고, 백엔드 전환본과 쿠키·CSRF·결제 복귀 왕복을 검증한 뒤 함께 배포한다.

## 범위와 기존 설계와의 관계

이번 범위는 `apps/frontend/`의 공통 API 클라이언트, 인증 상태와 화면, 구매자 체크아웃·배송지·주문·결제 승인, 판매자 상품·이미지·판매 등록, 관련 설정·테스트다. [Google 로그인 연동과 현재 사용자 표시](google-login-and-current-user.md)의 로그인 왕복과 `/api/auth/me` 응답 계약은 유지하되, 해당 문서의 개발용 ID 헤더 유지와 보호 API 미연동 범위는 이 설계로 대체한다. 기존 구매·판매·결제 프론트엔드 명세의 `VITE_BUYER_ID`·`VITE_SELLER_ID` 및 ID 헤더 사용 지시도 해당 API에 한해 이 설계로 대체한다. [결제 승인 및 결과 화면 설계](../buyer/buyer-payment-confirmation-result.md)의 승인 응답 검증, `IN_PROGRESS` 추가 확인 횟수와 간격, 확정 결과별 화면 처리는 유지한다.

백엔드 코드·DB·소유권 연결 운영 작업, 판매자 가입·승인 화면, 로그아웃, JWT 갱신, 결제 취소·환불, 새 역할과 새 dependency는 범위에 포함하지 않는다. 프론트엔드 단독 전환본은 현 백엔드와 호환되지 않는다. 백엔드 전환 명세의 구현과 연동 검증이 배포 선행 조건이다.

## 요청 계약과 공통 전송 흐름

다음 API 호출에서 ID 헤더와 ID 인자를 제거한다.

| 영역 | 보호 API | 변경 요청 여부 |
| --- | --- | --- |
| 판매자 | `POST /api/products`, `POST /api/products/{productId}/images`, `GET /api/products/ready`, `POST /api/sales` | `POST` 세 개 |
| 구매자 | `POST /api/shipping-addresses`, `GET /api/checkout`, `POST /api/orders`, `POST /api/payments/confirm` | `POST` 세 개 |

보호 API의 요청은 `credentials: 'include'`로 보낸다. `GET /api/auth/me`의 기존 쿠키 요청 계약은 유지한다. `GET /api/sales`와 `GET /api/sales/{saleId}`에는 보호 요청 처리를 적용하지 않는다. `Idempotency-Key`, JSON 본문, 이미지 `FormData`, 결제 승인 본문 및 기존 응답의 도메인 ID 필드는 유지한다. 상품·판매 응답의 `sellerId`는 서버가 확정한 양의 안전 정수인지 검증하며, 프론트엔드 설정값이나 `users.id`와의 일치 여부를 검사하지 않는다.

`shared/api/apiClient.ts`는 보호 요청 표시를 받아 쿠키 전송과 CSRF 헤더 구성을 담당한다. 도메인 API 모듈은 보호 요청 여부와 기존 본문·응답 계약을 지정하고, feature의 hook은 화면 흐름을 처리한다. 공통 클라이언트가 구매자·판매자 ID나 화면 문구를 알 필요는 없다. 공개 요청의 기존 동작은 유지한다. 이 방식은 각 도메인 API에 토큰 조회를 반복하는 방식보다 누락 가능성이 작고, 전역 인증 상태 계층을 새로 만들지 않아도 된다.

백엔드 전환본의 `GET /api/auth/csrf`는 인증 쿠키를 포함한 `GET`으로 호출하며 `Cache-Control: no-store` 응답의 `{ "token": string, "headerName": string }`을 받는 계약으로 맞춘다. 두 값은 비어 있지 않은 문자열이어야 한다. 로그인 성공 후 `/api/auth/me` 확인이 끝나면 토큰 조회를 시작하고, 토큰이 아직 없거나 무효화된 상태에서 첫 변경 요청이 오면 전송 전에 다시 조회한다. 같은 시점의 여러 변경 요청은 하나의 토큰 조회 결과를 공유한다. 토큰 조회가 실패하면 변경 요청을 보내지 않고 원래 오류를 호출자에게 전달한다. 토큰은 현재 페이지의 메모리에만 보관하며 JWT, URL, `localStorage`, `sessionStorage`, 로그에 넣지 않는다. 브라우저 전체 이동을 거치는 로그인 후에는 새 페이지에서 새 토큰을 받는다.

인증 실패 `401 AUTH_UNAUTHENTICATED` 또는 `403 AUTH_CSRF_INVALID`가 오면 보관한 토큰을 폐기한다. CSRF 오류 후 다음 사용자 재시도에서는 새 토큰을 조회한다. 실패한 `POST`를 공통 클라이언트가 자동 재전송하지 않는다. 특히 주문 생성의 `Idempotency-Key`와 결제 승인의 결과 판단을 투명한 재시도 로직으로 변경하지 않는다. 인증 쿠키가 없는 요청에 대한 `401` 우선 처리와 CSRF 검증 실패 시 서비스 미실행은 백엔드 계약을 따른다.

## 화면 상태와 결제 복귀

체크아웃과 두 판매자 페이지는 기존 `useCurrentUser` 조회가 끝나기 전에는 보호 API 호출이나 등록 기능을 시작하지 않는다. `401`이면 현재 경로를 유지하는 기존 Google 로그인 시작 동작을 제공한다. 조회 실패는 비로그인으로 단정하지 않고 재확인을 제공한다. `/api/auth/me`의 `roles`는 판매자 권한 판정에 사용하지 않으며, 실제 연결 부재는 보호 API의 `403`으로 확인한다.

| 보호 API 결과 | 화면 처리 |
| --- | --- |
| `401 AUTH_UNAUTHENTICATED` | 로그인 필요를 표시하고 사용자 재로그인을 안내한다. 이미 성공한 변경 결과를 실패로 단정하지 않는다. |
| `403 AUTH_BUYER_LINK_REQUIRED` | 체크아웃·배송지·주문에서는 구매자 연결이 필요한 계정임을 안내하고 해당 작업을 중단한다. |
| `403 AUTH_SELLER_LINK_REQUIRED` | 상품·이미지·판매 등록 및 등록 가능 상품 조회에서는 판매자 연결이 필요한 계정임을 안내하고 해당 작업을 중단한다. 별도의 셀프 가입·승인 화면은 추가하지 않는다. |
| `403 AUTH_CSRF_INVALID` | 요청을 자동 반복하지 않고 다시 시도할 수 있음을 안내한다. 다음 시도 전에 새 CSRF 토큰을 받는다. |
| 그 밖의 오류 | 기존 도메인 오류 코드별 안내와 재시도 규칙을 유지한다. |

구매자 체크아웃 Query key에서 개발용 `buyerId`를 제거한다. 로그인 왕복은 브라우저 전체 이동이므로 이전 페이지의 Query cache는 재사용되지 않는다. 체크아웃의 주문 요청이 인증·CSRF 문제로 거절되면 토스 결제창을 열지 않는다. 기존 주문 생성 `Idempotency-Key`와 결제 시도 처리의 보수적인 재시도 규칙은 유지한다.

토스 성공 경로에서는 URL의 `paymentKey`·`orderId`·`amount`를 기존 규칙으로 검증한 후, `/api/auth/me`로 로그인 상태를 확인하고 CSRF 토큰을 준비해야 승인 요청을 시작한다. 인증이 만료됐거나 토큰 준비에 실패하면 승인 요청을 시작하지 않는다. `/api/auth/me`에는 구매자 연결 정보가 없으므로 연결 부재는 승인 API의 `403 AUTH_BUYER_LINK_REQUIRED`로 확인한다. 승인 요청 도중 `401`, `AUTH_BUYER_LINK_REQUIRED`, `AUTH_CSRF_INVALID`가 발생해도 자동 로그인·자동 승인 재시도·결제 실패 표시를 하지 않고 `결제 결과를 아직 확인할 수 없습니다.`라는 결과 확인 필요 상태로 이동한다. 복귀 화면에 결제 키를 저장하지 않으며, 기존 설계대로 성공 URL의 필수 매개변수를 임의로 제거하지 않는다. 결과 확인 필요 화면은 새 결제를 권하지 않고 상품 목록으로 돌아가는 중립적인 링크만 제공한다. 정상 인증과 승인 중 응답에서는 기존 15초 간격의 추가 확인 최대 5회를 그대로 적용한다.

## 검증과 구현 선행 조건

- API 계약 테스트에서 8개 보호 요청의 ID 헤더 부재, 쿠키 포함, `GET`과 `POST`의 CSRF 헤더 차이, `Idempotency-Key`·`FormData` 유지, 서버 `sellerId` 검증을 확인한다.
- 공통 클라이언트 테스트에서 로그인 후·첫 변경 요청의 토큰 조회, 동시 요청 공유, 응답 헤더 이름 사용, 토큰 조회 실패 시 변경 요청 미전송, `401`·CSRF 오류 후 토큰 폐기, 실패한 변경 요청의 자동 재전송 부재를 확인한다.
- 화면 테스트에서 인증 확인 전 보호 호출 차단, 로그인 필요·연결 부재·CSRF 오류 구분, 공개 판매 조회 유지, 체크아웃·판매자 등록의 재시도 동작을 확인한다.
- 결제 복귀 테스트에서 인증 만료·연결 부재·CSRF 준비 실패 및 승인 중 인증 오류에 결제 완료·실패를 단정하지 않고 결과 확인 필요로 전환하는지 확인한다. 결제 키 비저장, 자동 로그인·승인 재시도 부재와 기존 `IN_PROGRESS` 횟수 제한도 확인한다.
- 프론트엔드 `npm run test`, `npm run build`, `npm run lint`를 실행한다. 백엔드 전환본과 동일 사이트 쿠키 또는 허용된 SPA origin의 자격 증명 CORS·CSRF 헤더 preflight를 실제 브라우저에서 검증한다.

공통 클라이언트의 쿠키 인증·CSRF 처리 방식은 여러 기능에 공통 적용되는 새 아키텍처 결정이다. 구현 전에 `docs/architecture/decisions/README.md` 형식에 따라 ADR로 기록하고, 기존 프론트엔드 아키텍처 규칙이 바뀌면 `docs/architecture/frontend.md`도 갱신한다. 백엔드의 ID 연결·CSRF 구현과 REST Docs 계약이 준비되면 이 문서의 토큰 응답 필드와 오류 코드를 대조한다. 두 계약이 다르면 프론트엔드를 임의로 추측해 구현하지 않고 연동 계약을 먼저 일치시킨다.
