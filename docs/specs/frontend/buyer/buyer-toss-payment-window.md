# 구매자 체크아웃 토스페이먼츠 주문서형 결제 설계

## 목적과 완료 조건

구매자가 체크아웃에서 배송지와 결제수단을 선택하고 필수 약관에 동의한 뒤 `결제하기` 버튼을 누르면 서버에 주문을 먼저 생성한다. 그 주문의 식별자와 확정 금액으로 토스페이먼츠 결제창을 연다. 이번 범위는 결제 **요청과 인증 결과 안내**까지다. 결제 승인 API와 주문의 결제 완료 처리는 포함하지 않는다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- 체크아웃 조회와 결제 설정이 유효하고 위젯 렌더링이 완료되면 `결제하기` 버튼을 사용할 수 있다. 버튼을 누른 시점에 배송지와 현재 결제수단 선택을 검사하고, 약관 변경 이벤트로 미동의가 확인된 경우 함께 안내하며 주문을 생성하지 않는다. 약관 초기 상태를 알 수 없으면 미동의로 단정하지 않고 SDK의 결제 요청 검증 결과를 안내한다. 선택 상태가 바뀌어도 안내를 실시간 갱신하지 않고 다음 클릭에서 다시 검사한다.
- 버튼 클릭 시 선택한 배송 정보로 `POST /api/orders`를 한 번 요청하고, 중복 클릭과 같은 요청의 재시도로 주문을 중복 생성하지 않는다.
- 주문 응답의 `paymentOrderId`, 상품명과 확정 금액을 사용해 토스페이먼츠 v2 주문서형 결제를 요청한다. 화면의 예상 금액을 결제 요청의 원천으로 사용하지 않는다.
- 주문 생성 실패, 응답 불일치·만료, SDK 초기화·호출 오류와 인증 리다이렉트를 각각 이해할 수 있는 상태로 안내한다. 같은 페이지에서 사용자가 결제창을 닫으면 오류를 안내하지 않고 위젯을 유지한다.
- 인증 성공 리다이렉트를 결제 완료로 표현하지 않는다. 백엔드 승인 기능이 없는 동안 테스트 클라이언트 키로만 검증하고 운영 결제에는 노출하지 않는다.
- 관련 프론트엔드 테스트, build와 lint를 통과한다.

## 기존 구조와 범위

[프론트엔드 아키텍처](../../../architecture/frontend.md), [디자인 지침](../../../DESIGN.md), 기존 [구매자 체크아웃 페이지 설계](buyer-checkout-page.md)를 따른다. 기존 설계에서 비활성으로 둔 `결제` 버튼의 후속 동작을 정의한다. [구매자 주문 생성 API](../../backend/order/buyer-order-creation-api.md)는 이미 `POST /api/orders`와 토스 결제 요청용 `paymentOrderId`를 제공한다. 현재 백엔드에는 결제 승인·취소·상태 조회 API와 `PAID` 상태 전이가 없다.

[구매자 체크아웃 목업](../../../mockups/buyer-checkout.html)은 왼쪽 열에 상품 정보·배송지·결제수단과 약관을 순서대로, 오른쪽 금액 정보 영역에 예상 총액·`결제하기` 버튼·상태 안내를 배치한다. 화면 너비가 1000px 이하이면 금액 정보 영역은 결제수단·약관 아래로 이동한다. 기본 URL에서는 예시 배송지를 미리 선택해 결제 영역을 확인할 수 있지만, 실제 구현에서는 사용자가 배송지를 명시적으로 선택해야 한다. 목업의 결제수단 라디오와 약관 체크박스는 SDK가 렌더링할 UI의 예시이며, 실제 결제수단·약관 구성은 토스 결제 어드민 설정을 따른다. `?payment=ready`는 선택 전 상태를, `?payment=loading`, `?payment=processing`, `?payment=error`, `?payment=cancel`, `?payment=success`, `?payment=fail`은 각 상태의 안내를 확인하는 목업 전용 URL이다. 목업은 실제 주문 API나 토스 SDK를 호출하지 않으며, 구현의 데이터·오류 계약은 이 문서를 따른다.

포함 범위는 `apps/frontend/`의 체크아웃 결제 버튼, 주문 생성 요청, 토스 SDK 호출, 인증 성공·실패 리다이렉트 안내, 설정과 관련 테스트다. 백엔드 코드·DB·주문 상태, 토스 `confirm` 호출, 결제 완료 화면, 환불, 웹훅, 로그인과 배송지 관리 기능은 변경하지 않는다. 주문을 먼저 생성하므로 사용자가 결제창을 닫거나 인증에 실패해도 기존 주문의 예약은 최대 3분 동안 유지되며, 이번 프론트엔드 작업은 이를 취소할 API를 추가하지 않는다.

## 연동 방식

체크아웃 목업은 결제수단과 필수 약관을 왼쪽 배송지 아래의 별도 결제수단 섹션에 표시하고, 오른쪽 금액 정보 영역에는 결제 버튼과 그 아래 상태 안내를 둔다. 실제 화면에서는 토스페이먼츠 **v2 주문서형** SDK가 왼쪽 결제수단·약관 영역을 렌더링하고, 오른쪽에 직접 만든 `결제하기` 버튼으로 결제를 요청한다. `widgets()` → `setAmount()` → `renderPaymentMethods()`·`renderAgreement()` → 버튼 클릭 → `requestPayment()` 순서를 따른다. 결제수단을 별도 창 안에서 선택하는 결제창형은 목업의 화면 흐름과 다르고, 결제창(구버전)은 신규 연동에 맞지 않아 선택하지 않는다. 모바일도 지원하기 위해 Promise 방식 대신 `successUrl`·`failUrl`을 쓰는 리다이렉트 방식을 선택한다. [주문서형 연동 가이드](https://docs.tosspayments.com/guides/payment-widget/integration), [주문서형 SDK](https://docs.tosspayments.com/sdk/v2/js/payment-widget)

공식 `@tosspayments/tosspayments-sdk`를 프론트엔드 dependency로 추가한다. 기존 dependency만으로 토스 주문서형 결제 UI를 렌더링할 수 없으며 공식 패키지의 타입과 초기화 계약을 사용한다. 브라우저에는 공개 가능한 주문서형 **클라이언트 키**만 `VITE_TOSS_CLIENT_KEY`로 제공한다. `VITE_*` 값이 번들에 포함되므로 시크릿 키나 토스 API 인증 값을 넣지 않는다. 실제 인증·승인 기능이 없는 이번 단계에서는 `VITE_TOSS_PAYMENT_PREVIEW_ENABLED=true`이고 클라이언트 키가 공식 테스트 키 접두사 `test`로 시작할 때만 SDK와 버튼을 활성화한다. 그 외 설정에서는 주문 생성과 SDK 호출을 막고 테스트 전용 기능 안내를 표시한다. 운영 배포에서는 미리보기 설정을 활성화하지 않는다. [토스페이먼츠 API 키 구분](https://docs.tosspayments.com/reference/using-api/api-keys)

현재 `VITE_BUYER_ID`는 예측 가능한 개발용 숫자이므로 토스의 `customerKey`로 전달하지 않는다. 이번 비회원 결제에는 공식 SDK의 `ANONYMOUS` 값을 사용한다. 실제 회원별 결제수단 기억이나 브랜드페이 연동은 별도로 설계한다. [SDK의 구매자 식별 규칙](https://docs.tosspayments.com/sdk/v2/js/payment-widget)

## 화면과 데이터 흐름

1. 기존 `GET /api/checkout`으로 상품·예상 금액과 저장 배송지 목록을 표시한다. 저장 배송지는 기존처럼 자동 선택하지 않는다. 미리보기 설정과 체크아웃 조회가 유효하면 예상 금액으로 `setAmount()`를 호출하고 왼쪽 배송지 아래 결제수단 섹션의 결제수단·약관 영역에 `renderPaymentMethods()`와 `renderAgreement()`를 호출한다. 예상 금액은 오른쪽 금액 정보 영역의 UI 표시용이며 결제 요청 전 주문 응답과 대조한다. 조회 실패, 위젯 렌더링 미완료, 등록·재조회 진행 중, 결제 설정 오류, 주문 생성 또는 SDK 처리 중에는 오른쪽 결제 버튼을 비활성화한다. 버튼 클릭 시 현재 결제수단은 SDK의 `getSelectedPaymentMethod()`로 확인한다. 약관은 `agreementStatusChange` 이벤트로 변경 상태를 확인하되 초기 이벤트가 없으면 동의 여부를 알 수 없는 상태로 둔다. 확인된 누락 항목은 버튼 아래에 안내하고 주문 요청을 막는다. 버튼 아래에는 진행·오류 상태를 표시하고, 테스트 결제이며 실제 결제 완료가 되지 않는다는 안내를 항상 표시한다.
2. 버튼 클릭 시 현재 목록에 있는 선택 배송지의 `recipientName`, `phoneNumber`, `postalCode`, `address`, `detailAddress`, `deliveryMessage`를 주문 요청의 `shippingAddress`로 복사한다. `addressName`과 `shippingAddressId`는 주문 API에 보내지 않는다. `saleId`와 `quantity`는 체크아웃 URL에서 검증한 값을 사용한다.
3. `crypto.randomUUID()`로 해당 주문 시도의 `Idempotency-Key`를 만들고 `X-Buyer-Id`와 함께 `POST /api/orders`를 호출한다. 동일한 요청을 네트워크 오류 등으로 재시도할 때는 같은 키를 재사용한다. 수량이나 배송지 선택이 바뀐 새 시도에는 새 키를 사용한다. 새로고침으로 페이지 메모리가 사라진 뒤에는 기존 시도를 복구하지 않으며, 이전 주문의 예약은 서버 만료 시각에 따라 해제된다.
4. 응답에서 `status === PENDING_PAYMENT`, canonical UUID v4 형식의 `paymentOrderId`, 양의 안전한 정수 `totalPrice`, 양의 정수 `quantity`, 상품명과 파싱 가능한 미래 `expiresAt`을 확인한다. 응답 수량·상품명이 요청 당시의 체크아웃 정보와 다르거나 확정 금액이 예상 금액과 다르면 결제 요청을 중단하고 정보 변경 안내와 체크아웃 다시 조회 동작을 제공한다. 갱신된 정보로 다시 결제 버튼을 누르면 새 멱등성 키로 새 주문 시도를 시작한다. 이전 주문의 예약은 만료 시각까지 유지된다. 확정 정보를 사용자의 기존 클릭만으로 조용히 결제하지 않는다. 상품명이 토스 `orderName`의 100자 제한을 넘거나 금액을 SDK의 `number`로 안전하게 표현할 수 없어도 결제창을 열지 않는다.
5. 검증을 통과하면 주문 응답의 `totalPrice`를 `KRW` 금액으로 `setAmount()`에 다시 전달하고 만료 시각과 현재 결제수단 선택, 이벤트로 확인된 약관 미동의를 재확인한 뒤 `requestPayment()`를 호출한다. 초기 약관 상태를 알 수 없으면 SDK가 필수 약관을 검증한다. SDK가 `NEED_AGREEMENT_WITH_REQUIRED_TERMS`를 반환하면 위젯과 유효한 기존 주문을 유지하고 약관 동의 안내를 표시한다. `orderId`에는 `paymentOrderId`, `orderName`에는 서버 응답의 상품명을 사용한다. 성공·실패 URL은 각각 `/payments/toss/success`, `/payments/toss/fail`로 구성한다. 현재 브라우저 origin을 포함한 절대 URL을 사용하고, 검증된 `saleId`와 `quantity`를 복귀 링크용 쿼리에 보존한다. 주문이 이미 만료됐으면 결제 요청 대신 새 주문 시도를 안내한다.
6. 같은 페이지에서 SDK가 명시적인 사용자 취소 코드 `USER_CANCEL`을 반환하면 오류 문구를 표시하지 않고 결제수단 위젯과 주문 응답·멱등성 키를 유지한다. 다시 누르면 아직 유효한 기존 주문으로 결제를 요청하고, 만료됐으면 새 주문 시도를 시작한다. SDK가 실패 URL로 보내는 취소 코드 `PAY_PROCESS_CANCELED`는 결과 페이지에서 안내한다. 리다이렉트 없이 SDK 요청이 그 밖의 오류를 반환하면 체크아웃에서 오류를 안내한다. 리다이렉트 후 체크아웃에 돌아왔을 때는 페이지 메모리가 없으므로 이전 주문을 복구하지 않는다. 위젯은 페이지당 한 번만 렌더링하고 화면 이탈이나 체크아웃 정보 변경으로 교체할 때 기존 인스턴스를 정리한다.

체크아웃 feature의 `api`는 주문 HTTP 요청과 토스 SDK 연동 경계를, `model`은 요청·응답 타입과 검증을, `hook`은 위젯 렌더링부터 주문 생성·결제 요청까지의 상태를 맡는다. UI는 SDK용 결제수단·약관 컨테이너, 배송지 선택, 버튼, 진행·오류 안내를 담당하고 HTTP·SDK를 직접 호출하지 않는다. `app/router.tsx`는 인증 결과 경로를 페이지에 연결한다. 기존 `requestApi`, `apiBaseUrl`과 `@tanstack/react-query` mutation 패턴을 재사용한다. 결제 상태를 전역 저장소에 두지 않는다.

## 인증 결과와 완료 경계

토스의 성공 리다이렉트에는 `paymentKey`, `orderId`, `amount`가, 실패 리다이렉트에는 오류 코드·메시지가 붙을 수 있다. 결과 페이지는 이 쿼리를 신뢰할 수 있는 결제 완료 증거로 해석하지 않는다. 성공 경로는 필수 매개변수가 형식상 있는지만 확인하고 **`결제 인증 경로로 돌아왔지만 결제가 완료되지 않았습니다.`**라고 안내한다. 매개변수가 없거나 잘못됐으면 결과를 확인할 수 없다고 안내한다. 실패 경로는 취소와 일반 실패를 구분해 간결한 안내 및 체크아웃 복귀 링크를 제공하고, 외부에서 받은 오류 메시지를 그대로 출력하지 않는다. 복귀 링크의 `saleId`·`quantity`도 기존 체크아웃 경로 규칙으로 검증한다. URL의 `paymentKey`나 배송 정보를 화면·로컬 저장소·로그에 남기지 않는다.

실제 결제 완료 기능은 후속 백엔드 설계가 필요하다. 그때 성공 리다이렉트에서 프론트엔드가 우리 백엔드 승인 API로 `paymentKey`, `orderId`, `amount`를 보내고, 백엔드가 저장된 주문의 `paymentOrderId`, 금액, 만료·상태를 검증한 뒤 서버 시크릿 키로 토스 `confirm`을 호출해야 한다. 토스 응답과 주문 상태를 서버에서 확정한 뒤에만 결제 완료 화면을 표시한다. 이번 설계는 그 API 계약이나 상태 전이·동시성 규칙을 임의로 확정하지 않는다. [토스페이먼츠 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

## 오류와 검증 전략

- 배송지·결제수단 미선택과 이벤트로 확인된 필수 약관 미동의는 버튼 클릭 시점에 검사해 버튼 근처에 함께 안내하고, 다음 클릭 전까지 선택 변화만으로 안내 문구를 바꾸지 않는다. 초기 약관 상태가 알려지지 않아 SDK가 결제 요청에서 미동의를 반환한 경우에도 같은 위치에 안내한다. 이때 이미 생성된 유효 주문은 다음 클릭에 재사용한다. 주문 생성의 판매 종료·재고 부족·멱등성 충돌은 서버 오류 코드에 맞는 안내를 제공하고 결제 요청을 하지 않는다. 네트워크·예상하지 못한 오류는 입력과 선택을 유지한 채 재시도할 수 있게 한다.
- 위젯 렌더링 중에는 `결제수단을 준비하는 중`, 주문 생성 중에는 `주문을 준비하는 중`, 결제 요청 중에는 `결제 진행 중`을 텍스트 상태로 알린다. SDK 초기화·렌더링·요청 오류가 나면 관련 위젯 인스턴스를 정리하고 재시도 경로를 제공한다. `USER_CANCEL`은 오류로 취급하지 않고 위젯을 유지한다. 결제창 취소를 결제 완료로 기록하지 않는다.
- 주문 API 테스트에서 헤더, 선택 배송지 스냅샷, 같은 요청 재시도의 멱등성 키 재사용, 응답 계약 오류와 예상·확정 금액 불일치를 검증한다.
- SDK를 경계에서 모의 처리해 결제수단·약관 렌더링, 초기 이벤트 없이 선택된 결제수단 조회, 이벤트로 확인된 미동의 안내와 주문 차단, SDK 약관 오류 후 주문 재사용, 예상 금액 표시와 서버 확정 금액 재설정을 확인한다. `requestPayment()`에 서버 `paymentOrderId`·상품명·절대 리다이렉트 URL이 전달되는지 확인한다. 중복 클릭, 같은 페이지에서 명시적인 취소 후 위젯·주문 유지, 취소 리다이렉트, 만료와 SDK 예외도 확인한다. 미리보기 설정이 없거나 라이브 클라이언트 키가 들어오면 주문 요청 전부터 결제 버튼이 비활성화되는지 검증한다.
- 결과 페이지 테스트에서 성공 리다이렉트가 결제 완료로 표시되지 않고, 실패 URL의 임의 메시지를 출력하지 않으며 복귀 링크가 정상 동작하는지 확인한다.
- 토스 테스트 클라이언트 키로 데스크톱·모바일의 결제창 열기와 성공·실패 리다이렉트를 수동 검증한다. 이 검증은 결제 승인을 확인하는 테스트가 아니다. 관련 Vitest 테스트와 프론트엔드 build·lint를 실행한다.

## 주요 결정

체크아웃 목업의 결제수단·약관 영역을 구현하기 위해 v2 주문서형을 사용한다. 주문 생성 응답을 결제 요청의 유일한 금액·식별자 원천으로 삼고, 리다이렉트 인증 결과를 결제 완료와 분리한다. 이번 선택은 구매자 체크아웃 한 기능의 외부 SDK 사용에 한정하며 공통 외부 연동 구조나 계층 의존 방향을 변경하지 않아 별도 ADR을 작성하지 않는다. 결제 승인과 주문 상태 전이는 후속 백엔드 설계 및 필요한 아키텍처 결정 기록에서 다룬다.
