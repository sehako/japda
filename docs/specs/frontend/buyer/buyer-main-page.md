# 구매자 메인 페이지 설계

## 목적과 완료 조건

구매자가 서비스에 진입해 월간 달력에서 조회 가능한 판매일을 선택하고, 해당 날짜의 판매 상품을 한눈에 확인할 수 있는 메인 페이지를 제공한다. 현재는 판매 일정 탐색에 집중하며 로그인, 상품 상세와 구매 흐름은 후속 작업을 위한 UI 경계만 둔다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- `/`에 직접 접근하면 구매자 메인 페이지가 표시된다.
- 최초 진입 시 `Asia/Seoul` 기준 오늘이 선택되고 오늘의 판매 상품 목록을 조회한다.
- 월간 달력에서 과거 날짜, 오늘과 내일을 선택할 수 있다.
- `Asia/Seoul` 기준 모레 이후 날짜는 비활성화되어 선택하거나 조회할 수 없다.
- 선택 날짜가 바뀌면 `GET /api/sales?saleDate=YYYY-MM-DD`로 해당 날짜의 상품을 조회한다.
- API가 반환한 순서대로 모든 상품을 동일한 크기의 카드로 표시한다.
- 상품 카드는 대표 이미지, 판매 상태, 상품명과 가격만 표시한다.
- 상품 카드에는 클릭, 링크 또는 구매 동작이 없다.
- 헤더에 로그인 버튼이 표시되지만 현재는 클릭해도 인증, 이동 또는 modal 동작을 수행하지 않는다.
- 목록의 loading, 빈 결과, 오류와 재시도 상태를 서로 구분해 표시한다.
- 모바일과 데스크톱에서 달력과 상품 목록을 사용할 수 있고 키보드와 보조 기술로 선택 상태를 인식할 수 있다.
- 기존 판매자 페이지 경로와 Not Found 처리가 계속 동작한다.
- 프론트엔드 관련 테스트, lint와 build가 통과한다.

## 기존 구조와 선행 계약

프론트엔드는 `apps/frontend`의 Vite, React, TypeScript, TailwindCSS와 React Router 구성을 사용한다. [프론트엔드 아키텍처](../../../architecture/frontend.md)와 [디자인 지침](../../../DESIGN.md)을 따른다.

[구매자 메인 HTML 목업](../../../mockups/buyer-main.html)을 화면의 구현 기준 목업으로 사용한다.

상품 목록은 [구매자 판매 상품 목록 조회 API](../../backend/sale/buyer-sale-product-list-api.md)를 사용한다. 이 API는 인증 없이 단일 판매일을 조회하며 과거 날짜에는 하한을 두지 않고 `Asia/Seoul` 기준 내일까지 허용한다. 하루 판매 상품은 최대 20개이므로 pagination은 없다.

API 응답의 `quantity`는 판매 등록 당시의 최초 판매 수량이며 남은 재고가 아니다. 현재 API에는 잔여 재고, `SOLD_OUT`과 구매 가능 여부가 없으므로 메인 페이지는 `quantity`를 표시하거나 재고 상태를 추론하지 않는다.

판매 시작과 종료 시각은 상품별로 다르지 않다. 모든 판매는 `saleDate`를 기준으로 한국 시간 00:00에 시작해 다음 날 00:00에 종료된다. 상품 목록은 판매 시간으로 다시 정렬하지 않고 API가 보장하는 `createdAt ASC`, 동률이면 `saleId ASC` 순서를 그대로 유지한다.

## 라우팅과 호환성

`app` 계층의 route 구성은 다음과 같다.

| 경로 | 동작 |
| --- | --- |
| `/` | `BuyerMainPage` 표시 |
| `/seller/products/new` | 기존 `SellerProductRegistrationPage` 표시 |
| `/seller/sales/new` | 기존 `SellerSaleSchedulingPage` 표시 |
| 그 외 | 기존 Not Found 페이지 표시 |

현재 `/`의 `/seller/products/new` 이동은 제거한다. 기존 판매자 route의 URL과 페이지 동작은 변경하지 않으며 판매자 페이지로 이동하는 새 링크를 구매자 메인에 추가하지 않는다.

## 페이지와 화면 구성

구매자 메인은 별도의 hero나 소개 문구 없이 헤더 다음에 핵심 기능을 바로 배치한다. 화면은 다음 순서로 구성한다.

1. 구매자 헤더
   - 서비스 이름 `JAPDA`
   - 우측 로그인 버튼 `로그인`
2. 본문 2열 layout
   - 왼쪽 30%: `판매 일정` 제목과 월 이동 control이 포함된 월간 달력
   - 오른쪽 70%: 선택 날짜 제목, 동일한 크기의 상품 카드 grid와 조회 상태

```text
┌───────────────────────────────────────────────────────┐
│ JAPDA                                       [ 로그인 ] │
├──────────────────┬────────────────────────────────────┤
│ 판매 일정         │ 2026년 9월 10일                    │
│                  │ 오늘의 상품                        │
│ [이전] 9월 [다음] │                                    │
│ 일 월 화 수 목 금 토│ [상품 카드] [상품 카드] [상품 카드] │
│       1  2  3  4 5│ [상품 카드] [상품 카드] [상품 카드] │
│ 6  7  8  9 [10] 11│                                    │
│                  │                                    │
└──────────────────┴────────────────────────────────────┘
       30%                         70%
```

데스크톱에서는 콘텐츠 최대 폭을 `1440px`로 제한하고 달력과 상품 목록을 `3:7` 비율로 나눈다. 두 영역 사이에는 Concrete Gray 세로 구분선을 두며 왼쪽 달력은 상품 목록을 내려볼 때 viewport 안에 유지되도록 sticky 처리한다. 오른쪽 상품 카드는 가용 폭에 따라 3~4열로 표시한다.

좁은 화면에서는 2열 비율과 sticky를 해제하고 달력을 상품 목록 위에 쌓는다. 상품 카드는 화면 폭에 따라 1~2열로 전환한다. 달력은 항상 7열 구조를 유지하되 작은 화면에서도 날짜 버튼의 touch area와 선택 상태를 구분할 수 있어야 한다.

디자인은 흰 배경, Obsidian 텍스트, Concrete Gray 경계선과 사각형 카드라는 기존 원칙을 따른다. 카드에 gradient, shadow와 불필요한 radius를 사용하지 않는다. Signal Red는 현재 판매 중인 `LIVE` 상태에만 사용한다.

화면만 보고 알 수 있는 달력 사용법, 조회 가능 날짜 범위와 판매 시간 설명은 별도 문구로 반복하지 않는다. 장식용 영문 문구도 추가하지 않는다. 날짜의 선택 가능 여부는 실제 버튼 상태로 표현하고 loading, 빈 결과와 오류처럼 현재 상태를 이해하거나 다음 행동을 결정하는 데 필요한 문구만 표시한다.

## 헤더와 로그인 버튼

로그인 버튼은 후속 인증 기능의 위치와 시각적 우선순위를 확인하기 위한 빈 UI이다. native `button`과 `type="button"`을 사용하고 `로그인`이라는 명확한 이름을 제공한다. 현재 구현에서는 click handler, route 이동, modal, loading 상태와 인증 상태를 연결하지 않는다.

로그인 버튼을 비활성화하지는 않는다. 기본 CTA 형태를 유지하되 클릭 전후에 화면이나 애플리케이션 상태가 변하지 않는다. Google 로고, OAuth 공급자 이름과 로그인 성공·실패 상태는 표시하지 않는다.

## 월간 달력

### 날짜 기준

달력의 현재 날짜와 선택 가능 상한은 브라우저의 로컬 시간대가 아니라 `Asia/Seoul`을 기준으로 계산한다.

- 기본 선택 날짜: 페이지가 처음 열린 시점의 한국 날짜
- 선택 가능 날짜: 한국 날짜 기준 내일까지의 모든 날짜
- 선택 불가 날짜: 한국 날짜 기준 모레 이후
- 과거 하한: 없음
- API 요청 형식: `YYYY-MM-DD`

현재 월 이전으로는 제한 없이 이동할 수 있다. 다음 월 이동은 이동할 월에 선택 가능한 날짜가 하나라도 있을 때만 허용한다. 예를 들어 내일이 다음 달 1일이면 다음 달로 이동할 수 있지만, 그 밖의 다음 달은 이동할 수 없다.

달력은 일요일부터 토요일까지 7열로 표시한다. 현재 표시 월에 속하지 않는 앞뒤 날짜 칸은 빈 칸으로 두고, 인접 월 날짜를 중복 표시하거나 선택하게 하지 않는다. 월 제목에는 연도와 월을 함께 표시한다.

각 날짜는 native `button`으로 제공한다. 모레 이후 날짜 버튼에는 `disabled`를 적용한다. 선택 날짜에는 `aria-pressed="true"`에 대응하는 선택 상태를 제공하고, 오늘에는 선택 여부와 별개로 현재 날짜임을 전달하는 접근 가능한 이름 또는 상태를 제공한다. 색상만으로 오늘, 선택과 비활성 상태를 구분하지 않는다.

날짜를 선택하면 선택 상태를 먼저 갱신하고 해당 날짜의 목록을 조회한다. 이미 선택된 날짜를 다시 누르면 재조회하지 않는다. 월 이동만으로 선택 날짜나 상품 목록을 바꾸지 않는다.

페이지를 한국 시간 자정까지 계속 열어 둔 경우 오늘과 선택 가능 상한을 다시 계산한다. 새로 내일이 된 날짜를 활성화하고, 기존 선택 날짜는 유지하며 그 날짜의 목록을 다시 조회해 시간 기반 판매 상태를 갱신한다.

## 상품 목록과 카드

선택 날짜가 변경될 때마다 다음 공개 API를 호출한다.

```http
GET /api/sales?saleDate={YYYY-MM-DD}
```

구매자 또는 판매자 식별자 header는 전송하지 않는다. `saleDate`에는 달력에서 선택한 한국 날짜 문자열을 그대로 사용하며 `Date.toISOString()`으로 변환하지 않는다.

응답의 `sales` 배열 순서를 변경하지 않고 그대로 렌더링한다. 각 상품은 같은 구조와 크기의 `article`로 표시하고 `a`, `button`, click handler와 키보드 activation을 추가하지 않는다. 클릭 가능한 것처럼 보이는 pointer cursor, hover 이동과 hover shadow도 제공하지 않는다.

카드에는 다음 정보만 표시한다.

| 정보 | 표시 방식 |
| --- | --- |
| `representativeImagePath` | 카드 상단의 정사각형 대표 이미지 |
| `status` | 이미지 또는 상품 정보와 인접한 상태 tag |
| `name` | 상품명 |
| `price` | 천 단위 구분 기호와 `원`을 사용한 원화 가격 |

`saleId`, `productId`, `description`, `quantity`, `saleDate`, `startsAt`과 `endsAt`은 카드에 표시하지 않는다. 화면의 목록 제목이 선택 날짜를 제공하고 모든 상품의 판매 시간이 동일하므로 날짜와 시각을 카드마다 반복하지 않는다.

판매 상태는 다음과 같이 표현한다.

| API 상태 | 화면 문구 | 표현 |
| --- | --- | --- |
| `UPCOMING` | `UPCOMING` | 기본 흑백 tag |
| `ON_SALE` | `LIVE` | Signal Red tag |
| `ENDED` | `ENDED` | 낮은 강조의 gray tag |

클라이언트는 응답 상태를 현재 시각으로 다시 계산하지 않는다. API가 제공하지 않는 `SOLD_OUT`, 잔여 수량과 구매 가능 여부를 추론하지 않는다.

## 대표 이미지

API의 `representativeImagePath`는 `/products/...` 형식의 상대 경로이다. `shared/config/env.ts`에서 환경별 `VITE_IMAGE_BASE_URL`을 읽고 상대 경로와 결합해 이미지 URL을 구성한다. 기준 URL 뒤와 상대 경로 앞의 `/`를 정규화해 이중 구분자가 생기지 않게 한다.

`VITE_IMAGE_BASE_URL`이 없거나 유효한 URL이 아니면 상품 목록 조회 자체를 막지 않고 해당 카드에 중립적인 이미지 대체 영역을 표시한다. 구성된 이미지의 load가 실패해도 같은 대체 영역으로 전환한다. 대체 영역은 상품명을 접근 가능한 설명으로 사용하고 오류 세부 정보나 객체 경로를 노출하지 않는다.

이미지는 카드 너비와 같은 정사각형 영역을 차지하고 비율을 유지한 채 `object-fit: cover`로 표시한다. 이미지 로딩 때문에 카드의 크기나 목록 배치가 크게 이동하지 않도록 영역을 미리 확보한다.

## 조회 상태와 오류 처리

상품 목록 상태는 선택 날짜와 함께 관리한다.

| 상태 | 화면 동작 |
| --- | --- |
| 최초 조회 중 | 목록 위치를 유지하는 loading 표시 |
| 조회 성공 | 응답 순서의 상품 카드 표시 |
| 정상 빈 결과 | `선택한 날짜에 판매 상품이 없습니다.` 표시 |
| 조회 실패 | 오류 안내와 `다시 시도` 버튼 표시 |
| 재조회 중 | 오류를 제거하고 동일 날짜의 loading 표시 |

날짜를 변경하면 진행 중인 이전 요청을 `AbortController`로 취소한다. 컴포넌트가 해제될 때도 요청을 취소한다. 취소된 요청은 사용자 오류로 표시하지 않으며, 늦게 도착한 이전 날짜의 성공 또는 실패 응답이 현재 날짜 상태를 덮지 않게 한다.

오류 화면은 백엔드의 내부 메시지나 상대 이미지 경로를 그대로 노출하지 않는다. 공통 `requestApi`가 제공하는 네트워크·API 오류 구분을 사용하되 사용자가 할 수 있는 행동은 동일 날짜의 재시도 하나로 제한한다. 마지막 성공 목록을 다른 날짜의 결과처럼 남겨 두지 않는다.

## API 계약과 런타임 검증

API 모듈은 기존 `shared/api/requestApi`와 `apiBaseUrl`을 재사용한다. 성공 응답이 다음 형상을 만족하는지 런타임에서 검사한다.

```ts
type BuyerSaleStatus = 'UPCOMING' | 'ON_SALE' | 'ENDED'

type BuyerSaleProduct = {
  saleId: number
  productId: number
  name: string
  description: string | null
  price: number
  quantity: number
  saleDate: string
  startsAt: string
  endsAt: string
  status: BuyerSaleStatus
  representativeImagePath: string
}

type BuyerSaleProductListResponse = {
  sales: BuyerSaleProduct[]
}
```

화면에서 일부 필드를 표시하지 않더라도 전체 응답 계약을 확인한다. 식별자, 가격과 수량은 안전한 양의 정수, 날짜와 시각은 계약된 문자열, `sales`는 배열이어야 한다. 계약에 맞지 않는 성공 응답은 정상 빈 결과로 취급하지 않고 목록 조회 오류로 처리한다.

전체 데이터 흐름은 다음과 같다.

```text
BuyerMainPage
     ↓
선택 날짜와 월간 달력 UI
     ↓
useBuyerSales(selectedDate)
     ↓
fetchBuyerSales(saleDate, AbortSignal)
     ↓
GET /api/sales?saleDate=YYYY-MM-DD
     ↓
loading / empty / error / BuyerSaleCard 목록
```

선택한 날짜만 요청하고 오늘·내일 또는 인접 월을 미리 조회하지 않는다. 같은 날짜를 다시 선택하는 동작은 없으므로 별도 응답 cache나 Query library를 도입하지 않는다.

## 프론트엔드 구조와 책임

기존 `app → pages → features → shared` 의존 방향을 유지한다.

```text
src/
├── app/
│   └── router.tsx
├── pages/
│   └── buyer-main/
│       └── BuyerMainPage.tsx
├── features/
│   └── buyer-sale/
│       ├── api/
│       │   └── buyerSaleApi.ts
│       ├── hook/
│       │   └── useBuyerSales.ts
│       ├── model/
│       │   └── buyerSale.ts
│       └── ui/
│           ├── BuyerSaleCalendar.tsx
│           ├── BuyerSaleCard.tsx
│           └── BuyerSaleList.tsx
└── shared/
    ├── api/
    │   └── apiClient.ts
    └── config/
        └── env.ts
```

- `app/router.tsx`: `/`를 구매자 페이지에 연결하고 기존 route를 보존한다.
- `BuyerMainPage`: 헤더와 `3:7` 본문 안의 달력·상품 목록을 조합한다. API를 직접 호출하지 않는다.
- `buyerSaleApi`: 요청 URL 구성, `AbortSignal` 전달과 성공 응답의 런타임 형상 검사를 담당한다.
- `useBuyerSales`: 한국 시간의 오늘, 표시 월, 선택 날짜, 목록 요청 상태, 요청 취소, 재시도와 자정 경계 갱신을 조율한다.
- `buyerSale` model: 한국 날짜 문자열과 달력 월 계산, 선택 가능 여부, 가격·상태 표시 변환 및 이미지 URL 결합을 담당한다.
- `BuyerSaleCalendar`: 계산된 날짜와 상태를 렌더링하고 월 이동·날짜 선택 event만 전달한다.
- `BuyerSaleList`: loading, 빈 결과, 오류와 카드 목록을 구분한다.
- `BuyerSaleCard`: 전달받은 상품을 비상호작용 카드로 표시한다.

로그인 버튼과 구매자 헤더는 현재 구매자 메인 한 곳에서만 사용하므로 페이지 내부에 둔다. 실제로 둘 이상의 페이지에서 동일한 역할로 재사용될 때 별도 feature 또는 shared UI 추출을 검토한다.

이번 설계는 기존 계층과 API·이미지 계약을 적용하는 프론트엔드 기능이므로 새로운 계층, 모듈 경계 또는 외부 시스템 연동 방식을 결정하지 않는다. 별도 ADR은 작성하지 않는다.

## 접근성과 반응형 동작

- 월 이동과 날짜 선택에는 native `button`을 사용하고 키보드 focus가 명확히 보이게 한다.
- 비활성 미래 날짜는 시각적 비활성 표현과 실제 `disabled` 상태를 함께 제공한다.
- 선택 날짜, 오늘과 판매 상태를 색상에만 의존해 전달하지 않는다.
- 달력의 월 제목과 상품 목록 제목은 heading 순서를 유지한다.
- loading과 오류 상태 변화는 보조 기술이 인식할 수 있는 상태 영역에서 전달한다.
- 상품 이미지는 상품명을 반영한 대체 텍스트를 제공하고 대체 영역도 같은 크기를 유지한다.
- 상품명과 가격이 길어져도 카드 간 높이와 정보 계층이 무너지지 않게 한다.
- 모바일에서 가로 스크롤을 기본 탐색 방식으로 사용하지 않는다.
- 좁은 화면에서는 달력과 상품 목록을 세로로 쌓고 sticky 동작을 해제한다.

## 검증 전략

### model

- 한국 시간 기준 오늘 문자열을 `YYYY-MM-DD`로 계산하는지 검증한다.
- 과거, 오늘과 내일을 선택 가능하게 하고 모레 이후를 거절하는지 검증한다.
- 월말·연말과 윤년 경계에서 오늘·내일 및 월 이동 상한을 올바르게 계산하는지 검증한다.
- 달력의 첫 요일과 월별 날짜 수를 올바르게 계산하는지 검증한다.
- 원화 가격과 판매 상태를 계약된 화면 문구로 변환하는지 검증한다.
- 이미지 기준 URL과 상대 경로를 올바르게 결합하고 잘못된 설정을 거절하는지 검증한다.

### API와 hook

- 선택 날짜를 URL encode해 `saleDate` 쿼리 파라미터로 전달하는지 검증한다.
- 인증 또는 판매자 식별자 header를 전송하지 않는지 검증한다.
- 정상 목록과 빈 배열을 구분하고 API 순서를 유지하는지 검증한다.
- 지원하지 않는 상태, 잘못된 필드 형상과 비정상 성공 응답을 오류로 처리하는지 검증한다.
- 날짜 변경, 컴포넌트 해제와 자정 갱신 시 기존 요청을 취소하는지 검증한다.
- 취소된 요청과 늦게 도착한 응답이 현재 상태를 오류나 이전 날짜 결과로 덮지 않는지 검증한다.
- 오류 후 재시도가 같은 날짜를 다시 요청하는지 검증한다.

### 페이지와 수동 확인

- `/`에서 오늘 선택, 달력과 상품 목록이 표시되는지 확인한다.
- 이전 월 이동과 내일이 포함된 다음 월의 제한적 이동을 확인한다.
- 모레 이후 날짜가 선택되지 않고 API 요청도 발생하지 않는지 확인한다.
- loading, 빈 결과, 오류, 재시도와 이미지 실패 상태를 확인한다.
- 상품 카드가 모두 같은 정보 구조와 크기를 가지며 클릭하거나 focus되지 않는지 확인한다.
- 로그인 버튼이 표시되고 focus·click할 수 있지만 화면 전환이나 상태 변경이 없는지 확인한다.
- 모바일과 데스크톱에서 달력 7열과 카드 grid가 화면 폭을 벗어나지 않는지 확인한다.
- 데스크톱에서 달력과 상품 목록이 `3:7` 비율과 세로 구분선으로 배치되고 달력이 scroll 중 유지되는지 확인한다.
- `/seller/products/new`, `/seller/sales/new`와 임의의 Not Found 경로가 기존대로 동작하는지 확인한다.
- 관련 frontend test와 `npm run lint`, `npm run build`를 실행한다.

## 주요 결정과 후속 작업

- 메인 페이지의 핵심은 월간 달력과 선택 날짜의 판매 상품 탐색이다.
- 별도의 hero나 소개 영역 없이 달력과 상품 목록을 헤더 바로 아래에 `3:7`로 배치한다.
- 모든 상품은 동일한 크기의 비상호작용 카드로 표시한다.
- 상품 순서는 클라이언트에서 바꾸지 않고 API 계약을 따른다.
- 최초 판매 수량을 잔여 수량처럼 사용하지 않으며 카드에서 제외한다.
- 로그인 버튼은 후속 Google OAuth2를 위한 빈 UI로만 둔다.
- 대표 이미지 제공 인프라가 준비되지 않은 환경에서도 목록 자체는 사용할 수 있게 대체 영역을 제공한다.

후속 작업은 각각 별도 설계 대상으로 다룬다.

- Google OAuth2 로그인과 인증 상태
- 구매자 상품 상세와 카드 navigation
- 주문, 결제, 재고 차감과 품절 상태
- CloudFront 기반 이미지 제공과 배포 설정
- 검색, category, filter와 추천
