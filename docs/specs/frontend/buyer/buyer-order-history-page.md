# 구매자 주문 내역 페이지 설계

## 목적과 완료 조건

로그인한 구매자가 자신이 구매한 주문을 최신순으로 확인하고 각 주문의 결제 상태와 주문 시점의 상품·금액 정보를 이해할 수 있게 한다. 주문 내역은 백엔드가 인증 주체와 연결한 구매자 기준으로 조회하며, 프론트엔드는 구매자 식별자를 직접 전달하거나 주문 상태를 추론하지 않는다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- 로그인한 사용자가 `/orders`에 접근하면 `GET /api/orders`로 자신의 주문을 최신순 조회한다.
- 각 주문에 주문일, 주문 번호, 상품명, 수량, 단가, 총액과 주문 상태를 표시한다.
- 최초 20개를 표시하고 `nextCursor`가 있을 때만 사용자가 다음 주문을 불러올 수 있다.
- 추가 조회 결과는 기존 목록 아래에 중복 없이 이어 붙이며, 마지막 페이지에서는 추가 조회 동작을 제공하지 않는다.
- 로딩, 빈 목록, 최초 조회 실패, 추가 조회 실패, 비로그인과 구매자 연결 부재를 서로 구분해 안내한다.
- 작은 화면에서도 주문별 정보의 관계와 우선순위를 유지한다.
- API가 제공하지 않는 주문 상세, 배송, 취소·환불과 결제 수단 정보를 표시하거나 추론하지 않는다.
- 관련 프론트엔드 테스트, build와 lint를 통과한다.

## 기존 구조와 범위

[프론트엔드 아키텍처](../../../architecture/frontend.md)와 [디자인 지침](../../../DESIGN.md)을 따른다. PRD의 구매자 주문 내역 및 주문 상태 조회 요구를 프론트엔드 화면으로 제공한다. 백엔드에는 인증된 구매자의 주문을 조회하는 `GET /api/orders`가 이미 구현되어 있으므로 이 페이지는 해당 응답을 화면의 단일 원본으로 사용한다.

프론트엔드 구현 시 [구매자 주문 내역 HTML 목업](../../../mockups/buyer-order-history.html)을 화면 기준으로 삼고 정보 구조, 문구, 배치, 여백, 색상, 타이포그래피와 반응형 전환을 재현한다. 목업의 주문 데이터와 브라우저 내 `주문 더 불러오기` 동작은 예시이며 실제 데이터 흐름, API 요청·응답과 오류 처리는 이 문서의 계약을 우선한다. 목업의 `?state=` 매개변수는 빈 목록과 오류·인증 상태를 확인하기 위한 미리보기 용도이며 실제 route 상태 계약으로 사용하지 않는다.

포함 범위는 `apps/frontend/`의 `/orders` route, 주문 내역 page와 feature, 인증된 사용자의 주문 내역 진입 링크 및 관련 테스트다. 공통 헤더 추출과 기존 페이지 구조 리팩터링은 포함하지 않는다. 기존 인증 UI나 내비게이션 영역에 링크를 추가할 때도 현재 컴포넌트 경계를 유지한다. 새로운 dependency나 아키텍처 규칙은 필요하지 않다.

주문 상세 페이지, 상태·기간 필터, 검색, 사용자 지정 정렬, 번호 기반 페이지 이동, 배송 조회, 주문 취소, 환불, 결제 수단과 영수증은 포함하지 않는다. 백엔드 응답 확장, DB 변경과 새로운 주문 상태 추가도 이 문서의 범위 밖이다.

## 선행 조건

주문 목록 API는 쿠키 인증 주체를 요구하고 컨트롤러는 인증 주체가 없으면 `AUTH_UNAUTHENTICATED`를 반환한다. 그러나 현재 백엔드 인증 설정의 GET 보호 경로에 `/api/orders`가 포함되지 않은 상태이므로 실제 통합 환경에서 `JAPDA_ACCESS_TOKEN` 쿠키가 해당 요청의 인증 주체로 변환되는지 확인해야 한다.

페이지 출시 전 다음 중 하나로 선행 조건을 충족해야 한다.

- `/api/orders`를 백엔드의 인증 대상 GET 경로에 포함한다.
- 별도 수정이 불필요하다면 실제 브라우저 통합 테스트로 유효한 인증 쿠키 요청이 성공함을 확인한다.

프론트엔드에서 임시 구매자 ID나 `X-Buyer-Id`를 추가하는 방식으로 이 문제를 우회하지 않는다. 백엔드 인증 설정 수정이 필요하더라도 이는 별도 백엔드 작업으로 다룬다.

## 화면과 이동

### 진입 경로

주문 내역의 정식 경로는 `/orders`다. 로그인한 사용자가 구매자 메인 페이지의 기존 상단 인증·내비게이션 영역에서 `Orders` 링크를 통해 접근할 수 있게 한다. 메인 페이지와 주문 내역 페이지는 `Shop`, `Orders`와 현재 사용자 정보를 같은 순서로 표시하고 현재 위치를 구분한다. 작은 화면에서도 두 메뉴를 숨기지 않아 상품 목록과 주문 내역을 직접 오갈 수 있게 한다. 링크 추가를 위해 페이지별 헤더를 공통 컴포넌트로 추출하거나 전역 레이아웃을 새로 만들지 않는다. 비로그인 사용자의 링크 노출 여부와 관계없이 `/orders` 직접 접근은 아래 인증 상태에 따라 처리한다.

페이지 제목은 `Orders`, 설명은 `구매한 상품과 주문 상태를 확인할 수 있습니다.`로 한다. 목록의 각 행은 하나의 주문을 나타낸다. 주문 상세 API와 화면이 없으므로 행 전체나 주문 번호를 상세 링크처럼 표현하지 않는다.

### 주문 행

주문 행에는 다음 정보를 표시한다.

- `createdAt`: 사용자의 로컬 시간대로 변환한 주문일
- `orderId`: `주문 번호 #N` 형식
- `productName`: 주문 시점의 상품명
- `quantity`, `unitPrice`: `수량 N개 × M원` 형식
- `totalPrice`: `주문 금액 M원` 형식으로 단가보다 강조
- `status`: 상태 badge
- `expiresAt`: `PENDING_PAYMENT` 주문에서만 `결제 기한` 보조 정보로 표시

금액은 정수 원 단위로 천 단위 구분자를 적용한다. 날짜와 시각은 서비스의 기존 한국어 표시 관례를 따르며, 원본 시각을 임의로 잘라 표시하지 않는다. 주문 번호는 축약하지 않는다.

데스크톱에서는 주문일과 상태를 행 상단에 두고, 상품·수량 정보와 주문 금액을 한 행 안에서 구분한다. 작은 화면에서는 같은 정보를 세로로 쌓되 주문일·상태, 상품명, 수량·단가, 총액, 주문 번호 순서의 정보 관계를 유지한다. 흰 배경, 검은 기본 텍스트, 회색 경계와 divider를 사용하고 장식용 그림자·그라데이션·둥근 카드를 사용하지 않는다. 상태 badge에만 pill 형태를 허용한다.

### 상태 문구

백엔드가 제공하는 상태를 다음과 같이 표시한다.

| API 상태 | 화면 문구 | 의미 |
| --- | --- | --- |
| `PENDING_PAYMENT` | `결제 대기` | 결제 완료가 확인되지 않은 주문 |
| `PAID` | `결제 완료` | 결제가 승인되어 완료된 주문 |

`expiresAt`이 현재 시각보다 과거이더라도 프론트엔드가 주문을 `만료`로 재분류하지 않는다. 백엔드가 `PENDING_PAYMENT`를 반환하면 그대로 `결제 대기`로 표시하고 결제 기한만 보조 정보로 제공한다. 정의되지 않은 상태를 받으면 계약 오류로 처리하며 임의의 사용자 문구를 만들지 않는다.

## 목록 조회와 페이지네이션

페이지 진입 시 `GET /api/orders?size=20`을 호출한다. 보호 API 요청에는 기존 `requestApi`의 `protected: true`를 사용해 인증 쿠키를 포함한다. GET 요청이므로 CSRF 헤더를 별도로 추가하지 않는다.

응답은 다음 계약을 따른다.

```json
{
  "items": [
    {
      "orderId": 1000,
      "status": "PENDING_PAYMENT",
      "productName": "상품명",
      "quantity": 2,
      "unitPrice": 35000,
      "totalPrice": 70000,
      "createdAt": "2026-09-11T06:00:00Z",
      "expiresAt": "2026-09-11T06:03:00Z"
    }
  ],
  "nextCursor": "불투명한 cursor 또는 null"
}
```

`nextCursor`가 문자열이면 목록 아래에 `주문 더 불러오기` 버튼을 표시한다. 사용자가 버튼을 누르면 기존 `size=20`과 서버가 반환한 cursor로 다음 페이지를 요청하고, 성공한 항목을 기존 목록 아래에 이어 붙인다. `nextCursor`가 `null`이면 버튼을 표시하지 않는다. 추가 조회 중에는 기존 주문을 유지하고 버튼 위치에 진행 상태를 표시하며 중복 요청을 막는다.

cursor는 백엔드가 발급한 불투명 값으로 취급한다. 프론트엔드는 값을 해석·생성·변형하지 않고 다음 요청에 그대로 전달한다. 브라우저 저장소나 URL에 cursor와 누적 주문을 영속화하지 않는다. 새로고침하거나 페이지에 다시 진입하면 첫 페이지부터 조회한다. 번호 기반 페이지 이동, 이전 페이지와 자동 무한 스크롤은 제공하지 않는다.

## 컴포넌트 책임과 데이터 흐름

`app/router.tsx`가 `/orders`를 주문 내역 페이지에 연결한다. 페이지는 제목, 설명과 feature UI 배치를 담당한다. `buyer-order-history` feature의 `api`는 HTTP 요청과 응답 검증, `model`은 API 계약과 화면 모델, `hook`은 TanStack Query의 cursor 조회 상태, `ui`는 목록·주문 행·빈 상태·오류 상태를 담당한다. 페이지나 UI 컴포넌트에서 직접 API를 호출하지 않는다.

서버 상태는 `@tanstack/react-query`의 무한 조회 형태로 관리한다. 주문 조회는 `useCurrentUser`가 `authenticated`이고 사용자 정보가 있을 때만 활성화한다. query key에는 주문 내역이라는 안정적인 리소스 식별자, 현재 사용자의 `id`와 조회 크기를 포함하되 access token이나 백엔드의 buyer ID는 포함하지 않는다. 다음 페이지 매개변수는 직전 응답의 `nextCursor`만 사용한다. 조회 함수의 `AbortSignal`을 API 계층까지 전달하고 브라우저 포커스만으로 불필요하게 누적 목록을 다시 요청하지 않도록 재조회 정책을 명시한다. 사용자 `id`가 달라지면 서로 다른 cache를 사용하며, 로그아웃이 완료되면 주문 내역 query를 제거해 같은 브라우저의 다음 사용자가 이전 주문을 볼 수 없게 한다.

응답의 page와 item 구조, 양의 안전 정수인 식별자·수량·금액, 지원 상태, 파싱 가능한 시각과 `nextCursor` 형식을 런타임에서 검사한다. `totalPrice`를 `quantity × unitPrice`로 클라이언트에서 다시 계산해 대체하지 않고 서버 응답을 표시한다. 계약에 어긋난 성공 응답은 정상 주문으로 일부 표시하지 않고 해당 조회의 오류로 처리한다.

## 로딩, 빈 상태와 오류

최초 조회 중에는 주문 행의 정보 구조와 비슷한 skeleton 또는 접근 가능한 로딩 안내를 표시한다. 조회가 성공했지만 `items`가 비어 있으면 `아직 구매 내역이 없습니다.`와 상품 목록으로 이동하는 링크를 표시한다. 빈 첫 페이지가 `nextCursor`를 반환하는 비정상 계약은 응답 오류로 처리한다.

`useCurrentUser`가 `checking`이면 주문 API를 호출하지 않고 인증 확인 진행 상태를 표시한다. `unauthenticated`이면 주문 API를 호출하지 않고 로그인 필요 화면을 표시한다. 인증 상태 조회 자체가 실패하면 주문 조회 오류와 구분해 로그인 상태 확인 실패 및 재시도 동작을 제공한다. `authenticated`로 확인된 뒤 주문 API가 `401`을 반환하면 인증이 만료된 것으로 취급하고 로그인 필요 화면으로 전환한다.

오류는 다음과 같이 구분한다.

| 조건 | 화면 처리 |
| --- | --- |
| 인증 상태 확인 실패 | 주문 API를 호출하지 않고 로그인 상태 확인 실패와 `다시 시도` 버튼 제공 |
| `401 AUTH_UNAUTHENTICATED` | 로그인이 필요하다는 안내와 기존 로그인 진입 동작 제공 |
| `403 AUTH_BUYER_LINK_REQUIRED` | 현재 계정에 구매자 정보 연결이 필요하다는 안내 제공 |
| 최초 조회의 네트워크·서버·응답 계약 오류 | 목록 대신 조회 실패 안내와 `다시 시도` 버튼 제공 |
| 추가 조회 오류 | 기존 목록을 유지하고 목록 아래에 오류 안내와 `다시 시도` 버튼 제공 |
| `ORDER_CURSOR_INVALID` | 누적 페이지를 폐기하고 첫 페이지부터 다시 조회할 수 있게 안내 |
| 그 밖의 요청 매개변수 오류 | 내부 오류 정보를 노출하지 않고 일반 조회 실패로 처리 |

오류 응답의 `detail`, stack trace, cursor, 인증 정보와 내부 식별 관계를 화면이나 로그에 직접 출력하지 않는다. 재시도 시 최초 조회와 추가 조회를 구분하며, 추가 조회 실패 때문에 이미 표시한 주문을 제거하지 않는다. 오류, 진행과 상태 badge는 색상만으로 구분하지 않고 텍스트와 접근 가능한 상태 정보를 함께 제공한다.

## 검증 전략

- API 계약 테스트에서 `/api/orders`, `size=20`, 다음 cursor 전달, 보호 API 옵션과 `AbortSignal` 전달을 검증한다.
- 응답 검증 테스트에서 정상 page, 마지막 page, 빈 page와 잘못된 필드·상태·금액·시각·cursor 거절을 확인한다.
- hook 테스트에서 최초 조회, 다음 page 이어 붙이기, 마지막 page 중단, 중복 추가 요청 방지와 최초·추가 재시도를 검증한다.
- 목록 UI 테스트에서 주문 정보와 금액·날짜 형식, `PENDING_PAYMENT`·`PAID` 문구, 결제 기한 조건부 표시를 검증한다.
- 페이지 테스트에서 로딩, 빈 목록, 비로그인, 구매자 연결 부재, 최초 오류, 추가 오류와 재시도 상태를 검증한다.
- 인증 사용자 변경이나 로그아웃 뒤 이전 사용자의 주문 내역이 화면과 query cache에서 노출되지 않는지 확인한다.
- router 테스트에서 `/orders` 연결과 기존 경로의 동작 유지를 확인한다.
- 관련 Vitest 테스트와 프론트엔드 build·lint를 실행하고 데스크톱·모바일 배치를 브라우저에서 확인한다.
- 백엔드 선행 조건을 충족한 환경에서 유효한 쿠키의 정상 조회, 비로그인 `401`, 구매자 연결 부재 `403`을 통합 확인한다.

## 주요 결정

현재 백엔드 계약만 사용해 최신순 주문 목록을 제공한다. API가 cursor 기반 단방향 조회만 지원하므로 명시적인 `주문 더 불러오기` 동작을 사용하고 번호 기반 페이지네이션이나 자동 무한 스크롤을 추가하지 않는다. 주문 상태와 총액은 서버 응답을 그대로 신뢰하며 만료·배송·취소·환불 상태를 클라이언트에서 추론하지 않는다. 주문 상세 계약이 없으므로 목록 행에 상세 이동 동작을 제공하지 않는다.

기존 프론트엔드 계층, TanStack Query와 보호 API 호출 방식을 그대로 사용한다. 계층·모듈·도메인 경계나 공통 외부 연동 방식을 변경하는 새로운 아키텍처 결정은 없어 별도 ADR을 작성하지 않는다.
