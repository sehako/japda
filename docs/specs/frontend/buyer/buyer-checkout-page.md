# 구매자 체크아웃 페이지 설계

## 목적과 완료 조건

구매자가 판매 상품 상세에서 구매 수량을 정하고 `구매하기`를 누르면, 체크아웃 페이지에서 해당 수량의 상품 정보와 서버가 계산한 예상 금액을 확인하고 배송지를 설정할 수 있게 한다. 이 페이지는 주문 전 확인 단계이며 주문 생성과 결제는 수행하지 않는다.

다음 조건을 모두 만족하면 완료된 것으로 본다.

- 판매 중인 상품 상세에서 양의 구매 수량을 선택하고 `구매하기`를 누르면 해당 판매 일정의 체크아웃 페이지로 이동한다.
- 체크아웃 페이지는 선택한 수량으로 `GET /api/checkout`을 호출하고 상품명, 대표 이미지, 단가, 수량과 예상 총액을 표시한다.
- 저장 배송지가 있으면 사용자가 하나를 명시적으로 선택하고 그 배송 정보를 확인할 수 있다.
- 저장 배송지가 없으면 안내와 `배송지 등록` 버튼을 보여주며, 버튼을 누르면 같은 페이지에 등록 양식을 펼친다.
- 배송지 등록에 성공하면 체크아웃 정보를 다시 조회하고 새 배송지를 선택한다.
- 금액 정보 아래에 비활성 `결제` 버튼을 표시하되 주문 생성이나 결제 동작은 수행하지 않는다.
- 유효하지 않은 경로·설정, 조회·등록 오류와 이미지 오류를 사용자에게 이해할 수 있는 상태로 표시한다.
- 기존 구매자·판매자 경로의 동작을 유지하고 관련 프론트엔드 테스트, build와 lint를 통과한다.

## 기존 구조와 범위

[프론트엔드 아키텍처](../../../architecture/frontend.md)와 [디자인 지침](../../../DESIGN.md)을 따른다. 기존 [구매자 판매 상품 상세 페이지 설계](buyer-sale-product-detail-page.md)는 `구매하기` 버튼을 동작 없는 UI로 두고 수량 선택을 제외한다. 이 문서는 그 버튼의 이동 동작과 수량 선택에 한해 기존 설계를 확장한다. 상세 조회 API의 `quantity`는 최초 판매 수량이며 남은 재고가 아니므로 수량 선택의 상한이나 재고 표시로 사용하지 않는다.

프론트엔드 구현 시 [구매자 체크아웃 HTML 목업](../../../mockups/buyer-checkout.html)을 체크아웃 페이지의 화면 기준으로 삼고, 정보 구조, 문구, 배치, 여백, 색상, 타이포그래피와 반응형 전환을 재현한다. 상품 상세의 수량 선택과 체크아웃 이동은 [구매자 판매 상품 상세 HTML 목업](../../../mockups/buyer-sale-product-detail.html)을 기준으로 구현한다. 체크아웃 목업에서 `?empty=1`로 열면 저장 배송지가 없는 상태와 등록 양식을 확인할 수 있으며, 이 상태도 구현 기준에 포함한다. 목업의 상품·배송지 데이터와 브라우저 내 모의 동작은 예시이므로 실제 데이터 흐름, API 요청·응답과 오류 처리는 이 문서의 계약을 우선한다.

기존 [구매자 체크아웃 조회 API](../../backend/order/buyer-checkout-api.md)는 `saleId`, `quantity`와 임시 구매자 식별자 `X-Buyer-Id`로 상품 정보 및 저장 배송지 목록을 반환한다. 목록 외에 배송지 단건 조회 API는 없다. 저장 배송지가 없으면 기존 [구매자 배송지 등록 API](../../backend/shipping-address/buyer-shipping-address-registration-api.md)를 호출한다. 두 API는 구매자 인증을 제공하지 않으므로 프론트엔드는 기존 개발용 판매자 식별자 설정 방식에 맞춰 `VITE_BUYER_ID`를 사용한다.

이번 변경은 `apps/frontend/`의 구매자 상세 화면, 체크아웃 페이지, 관련 feature·설정·route와 테스트에 한정한다. 백엔드 계약, DB, 로그인, 주문 생성, 재고 예약, 실제 결제, 배송지 수정·삭제·기본 배송지 설정, 외부 주소 검색은 변경하지 않는다. 새로운 dependency나 아키텍처 규칙은 필요하지 않다.

## 화면과 이동

### 상품 상세에서 수량 선택

기존 `/sales/:saleId` 상세 화면에 구매 수량 선택을 추가한다. 초기값은 `1`이며 양의 정수만 허용한다. 백엔드 `quantity` 매개변수가 `Int`이므로 최대 입력값은 `2,147,483,647`이다. 입력이 유효하지 않으면 필드 안내를 표시하고 구매하기 이동을 막는다. 수량 선택만으로는 API를 호출하지 않으며 기존 상세 조회 결과로 예상 총액이나 남은 재고를 계산해 표시하지 않는다.

`구매하기` 버튼은 기존처럼 상세 응답의 `status`가 `ON_SALE`일 때만 활성화한다. 활성 버튼을 누르면 선택 수량을 URL에 담아 `/checkout/:saleId?quantity=N`으로 이동한다. 상세 화면의 판매 상태는 이동 가능 여부만 결정하며 실제 구매 가능 여부를 보증하지 않는다.

### 체크아웃 화면

체크아웃 페이지는 URL의 `saleId`와 `quantity`를 읽는다. 둘 중 하나라도 양의 안전한 정수가 아니거나 `quantity`가 `Int` 범위를 넘으면 API를 호출하지 않고 잘못된 경로 안내와 상품 목록 이동 링크를 표시한다. URL에 수량이 없으면 임의의 기본값으로 조회하지 않는다. URL을 보존하므로 새로고침과 직접 접근 시에도 같은 수량을 조회한다.

유효한 입력과 `VITE_BUYER_ID`가 있으면 `GET /api/checkout?saleId=...&quantity=...`를 호출한다. 체크아웃 페이지에는 수량 수정 기능을 두지 않는다. 수량을 바꾸려면 상품 상세로 돌아가 다시 선택한다. 상품명, 대표 이미지, 단가, 선택 수량과 서버가 계산한 예상 총액을 한 영역에 명확히 표시한다. 체크아웃 API는 판매 기간과 잔여 재고를 판정하지 않으므로 이 화면도 구매 가능 여부나 남은 수량을 추론하지 않는다. 예상 금액은 주문 확정 금액으로 표현하지 않는다.

저장 배송지가 한 건 이상이면 배송지명과 수취인·연락처·주소·배송 메모를 확인할 수 있는 선택 목록을 표시한다. 서버가 기본 배송지를 지정하지 않으므로 첫 항목을 자동 선택하지 않는다. 선택한 배송지는 이 페이지의 임시 UI 상태이며 서버 저장값을 변경하지 않는다. 저장 배송지가 `[]`이면 `등록된 배송지가 없습니다.`라는 안내와 `배송지 등록` 버튼을 표시한다. 버튼을 누르기 전에는 등록 양식을 표시하지 않는다.

페이지는 `docs/DESIGN.md`의 체크아웃 화면 지침에 따라 흰 배경, 각진 입력, 회색 경계와 충분한 간격을 사용한다. 상품 이미지는 화면의 주요 시각 요소로 두고 장식용 그림자·그라데이션을 사용하지 않는다. 작은 화면에서는 상품 정보와 배송지 영역을 세로로 배치한다. 금액 정보 아래에 `결제` 버튼을 배치하되 실제 주문·결제 흐름이 연결되기 전까지 `disabled` 상태를 유지한다. 배송지 선택 여부로 활성화하지 않고 API 요청, 화면 이동 또는 상태 변경도 일으키지 않는다.

## 배송지 등록

빈 배송지 안내의 `배송지 등록` 버튼을 누르면 같은 페이지에 양식을 펼친다. 양식에는 배송지명, 수취인명, 전화번호, 우편번호, 기본 주소, 상세 주소와 선택 배송 메모를 둔다. 주소 검색·자동 완성은 제공하지 않는다. `등록 취소`는 양식을 닫고 빈 배송지 안내로 돌아가며 서버 요청을 보내지 않는다.

필수값과 길이는 등록 API 계약을 따른다. 필수 필드는 앞뒤 공백을 제외한 길이 `1` 이상이며 배송지명·수취인명은 최대 `100`, 전화번호는 `30`, 우편번호는 `20`, 기본·상세 주소는 `255`자다. 배송 메모는 선택이며 최대 `500`자다. 전화번호와 우편번호에 별도의 국가별 형식 규칙을 추가하지 않는다. 제출 시 `POST /api/shipping-addresses`에 `X-Buyer-Id`를 포함하고, 진행 중에는 중복 제출을 막는다.

등록 성공 응답의 `shippingAddressId`를 기억한 뒤 기존 체크아웃 조회를 무효화해 다시 가져온다. 갱신된 목록에 해당 ID가 있으면 그 배송지를 선택하고 양식을 닫는다. 등록은 성공했지만 재조회에 실패한 경우 등록 양식에서 재제출을 유도하지 않고, 등록 완료 사실과 목록 재시도 버튼을 표시한다. 재조회 성공 시 생성된 배송지 선택을 완료한다. 배송지가 다른 창에서 먼저 등록되어 빈 목록이 오래된 경우처럼 등록 API가 중복 또는 개수 제한 오류를 반환하면 오류를 표시하고 목록 재시도 경로를 제공한다.

## 데이터 흐름과 계약

`app/router.tsx`가 `/checkout/:saleId`를 새 페이지에 연결한다. 상세 UI는 선택 수량 상태와 이동만 담당한다. 새 페이지는 URL 및 화면 배치를 담당하고, 체크아웃 feature의 API·model·hook·UI가 조회, 등록, 응답 검증과 화면 상태를 처리한다. API 호출은 기존 `requestApi`와 `apiBaseUrl`, 서버 상태는 `@tanstack/react-query`를 사용한다. 새 `VITE_BUYER_ID`는 양의 안전한 정수로 검증하며 설정이 없거나 유효하지 않으면 요청을 보내지 않고 개발용 설정 오류를 표시한다. 기능 간 직접 의존과 전역 배송지 상태는 만들지 않는다.

체크아웃 조회의 query key에는 구매자 ID, 판매 일정 ID와 수량을 포함한다. 조회 함수의 `AbortSignal`을 API까지 전달하고 실패한 조회는 재시도할 수 있게 한다. 배송지 등록 mutation 성공 후 현재 체크아웃 query를 무효화해 재조회한다. 수량 선택 상태는 상세 페이지에만, 배송지 선택과 등록 양식 상태는 체크아웃 화면에만 둔다.

조회 성공 응답에서는 `saleId`, `productName`, `/`로 시작하는 `representativeImagePath`, 양의 `quantity`, 양의 `unitPrice`, `totalPrice`와 배송지 배열 및 각 필드의 형식을 런타임에서 검사한다. 응답의 `saleId`와 `quantity`가 요청값과 다르거나 금액이 JavaScript 안전 정수 범위를 벗어나면 정상 데이터로 표시하지 않는다. 대표 이미지 URL은 기존 `imageBaseUrl`과 상대 경로를 조합하고 이미지 주소가 없거나 로드에 실패하면 상품명을 설명으로 포함한 대체 영역을 보여준다. 등록 성공 응답에서는 생성된 배송지 ID와 필수 배송 필드를 검사한다. 계약에 어긋난 성공 응답은 해당 조회 또는 등록 오류로 처리한다.

## 오류와 상태

초기 조회 중에는 상품·배송지 영역의 로딩 상태를 표시한다. 체크아웃 조회의 `ORDER_SALE_NOT_FOUND`는 판매 상품을 찾을 수 없다는 안내와 상품 목록 링크로 처리한다. 그 밖의 HTTP·네트워크·응답 계약 오류는 상세 정보를 노출하지 않는 조회 실패 안내와 재시도 버튼으로 처리한다. `VITE_BUYER_ID` 설정 오류는 API 호출 전에 별도로 안내한다.

등록 양식의 필수값·길이를 먼저 검사하고, 서버의 배송 필드 오류는 해당 필드에 연결한다. 배송지명 중복과 10개 제한, 네트워크 오류는 양식 근처에 구체적으로 안내한다. 등록 실패 시 입력값을 유지하고 재시도를 허용한다. 오류 본문의 내부 정보나 구매자 식별자는 화면에 표시하지 않는다. 화면의 로딩·오류·선택 상태는 텍스트와 접근 가능한 상태 정보로 전달하고 색상만으로 구분하지 않는다.

## 검증 전략

- 상세 페이지에서 초기 수량, 양의 정수 검증, 수량 변경만으로 API를 호출하지 않는 동작, `ON_SALE`에서만 이동 가능한 버튼과 URL 전달을 검증한다.
- 체크아웃 API에서 `X-Buyer-Id`와 쿼리 매개변수, 응답 계약 및 불일치·잘못된 응답 거절을 검증한다.
- 체크아웃 페이지에서 잘못된 URL·설정, 로딩·404·일반 오류·재시도, 상품과 서버 예상 총액 표시, 수량 수정 부재 및 `결제` 버튼의 비활성 상태를 검증한다.
- 저장 배송지가 있는 경우의 명시적 선택과 빈 배송지의 안내·버튼·양식 열기 및 취소를 검증한다.
- 배송지 등록 요청·필드 오류·중복 제출 방지, 성공 후 체크아웃 재조회와 새 배송지 선택, 등록 성공 후 재조회 실패 상태를 검증한다.
- 관련 Vitest 테스트와 프론트엔드 build·lint를 실행하고 반응형 배치와 이미지 대체 영역을 브라우저에서 확인한다.

## 주요 결정

체크아웃 응답을 상품·금액·저장 배송지의 단일 원본으로 사용한다. 상세 페이지는 `saleId`와 구매 수량만 전달하며, 체크아웃 페이지에서 별도의 상세 조회나 배송지 목록 조회를 추가하지 않는다. 수량은 상세 페이지에서만 선택해 수량 조작 중 체크아웃 API 요청이 발생하지 않도록 한다. 배송지가 없는 경우에도 등록 양식을 즉시 펼치지 않고 사용자의 버튼 조작으로 연다. 기존 프론트엔드 계층과 기술을 그대로 사용하므로 새로운 ADR 대상 아키텍처 결정은 없다.
