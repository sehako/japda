# ADR-035: 결제 승인 transaction에서 정산 원천 스냅샷 생성

- 상태: 승인
- 적용 영역: backend
- 결정일: 2026-09-21

## 결정

PG 결제 승인 성공을 로컬 업무 상태에 반영할 때 `Payment` 승인, `Order` 결제 완료, 재고 예약 확정과 불변 `SettlementEntry` 생성을 하나의 PostgreSQL transaction에서 수행한다. 정산 원천에는 결제, 주문, 판매, 판매자, 지급 대상 사용자, 수량, 단가, 총액, PG 승인 시각과 서울 기준 정산일을 저장하고 `payment_id` unique 제약으로 멱등성을 보장한다.

일일 판매자 정산 배치는 승인 결제를 주문·판매·사용자 연결과 다시 조인해 구매별 정산 상세를 생성하지 않는다. 승인 시점에 생성된 `settlement_entries`를 결제별 정산 근거로 사용하고, 정산일과 최초 실행에서 고정한 ID 상한 안의 entry를 판매자별로 집계·검산한 뒤 기존 지갑과 원장 transaction으로 입금한다.

PG 성공 후 로컬 transaction이 실패하면 기존 `CONFIRMING` 결제 reconcile 흐름이 동일한 승인 적용을 다시 수행한다. 이미 승인된 결제의 재호출은 내용이 같은 정산 원천의 존재를 확인해야 하며, 원천이 없거나 내용이 다르면 성공으로 숨기지 않고 정합성 오류로 처리한다.

이 결정은 ADR-025의 결제별 정산 근거 생성 시점과 ADR-030의 collection 입력을 대체한다. 판매자별 정산, 사용자 귀속 지갑, 불변 원장, worker별 checkpoint와 최종 검산 계약은 유지한다.

## 이유

결제 승인과 정산 원천을 같은 transaction에 저장하면 결제는 성공했지만 정산 대상이 누락되는 상태를 구조적으로 차단할 수 있다. 판매자와 지급 대상, 금액을 승인 시점에 고정하면 이후 연결 변경과 운영 데이터 수정에도 과거 정산 귀속이 달라지지 않는다.

일일 배치가 1억 건의 결제마다 여러 업무 테이블을 조인하고 같은 정산 상세를 새로 쓰는 작업을 제거하면 결제별 감사 근거를 유지하면서 배치 시간의 반복 조회·쓰기 비용을 줄일 수 있다. 현재 API와 배치가 같은 PostgreSQL을 사용하므로 메시지 브로커와 최종 일관성 복구 절차를 추가하는 것보다 직접 transaction이 단순하고 강한 정합성을 제공한다.

## 트레이드오프

결제 승인 application이 정산 원천 저장 계약에 의존하며, 지급 대상 연결 누락이나 정산 테이블 장애가 로컬 결제 확정을 지연시킨다. PG가 이미 성공한 경우 기존 reconcile로 재시도할 수 있지만 영구 데이터 오류는 운영 대응이 필요하다. 서비스나 데이터베이스를 물리적으로 분리하면 같은 transaction을 사용할 수 없으므로 Outbox와 멱등 consumer를 포함한 새로운 결정이 필요하다.

승인 시점마다 정산 원천 행을 추가하므로 온라인 결제 transaction의 쓰기 비용과 저장 공간이 증가한다. 대신 일일 배치의 대규모 조인과 결제별 상세 생성 비용을 제거한다. 취소·환불은 승인 원천을 수정하지 않는 반대 정산 항목이 적합하지만 현재 범위에는 포함하지 않으며 별도 결정이 필요하다.
