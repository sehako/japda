# ADR-023: 구매자·판매자 식별을 인증 주체 연결로 전환하고 쿠키 API에 CSRF 보호 적용

- 상태: 승인
- 적용 영역: backend
- 결정일: 2026-09-14

## 결정

보호 대상 구매자·판매자 API는 `JAPDA_ACCESS_TOKEN` 쿠키의 JWT로 인증하고, `users.id`에서 DB에 등록된 구매자 또는 판매자 도메인 ID를 조회해 기존 서비스에 전달한다. `X-Buyer-Id`와 `X-Seller-Id`는 식별 근거로 사용하지 않는다. 구매자와 판매자 연결은 각각 `user_id`와 도메인 ID의 일대일 관계로 저장하며, 확인된 기존 소유권만 운영 절차에서 연결한다. 신규 사용자에게는 기존 ID 최댓값 이후의 DB 시퀀스 값으로 구매자 ID를 발급하고 연결한다. 기존 사용자에게 연결이 없으면 자동 추정하거나 새 ID를 부여하지 않는다.

쿠키 인증을 사용하는 상태 변경 요청에는 Spring Security의 CSRF 검증을 적용한다. 예상 토큰은 `HttpOnly` CSRF 쿠키에 저장하고, 인증된 SPA는 `GET /api/auth/csrf`에서 토큰과 헤더 이름을 받아 변경 요청에 사용한다. 인증 실패는 `401 AUTH_UNAUTHENTICATED`, 구매자·판매자 연결 부재는 각각 `403 AUTH_BUYER_LINK_REQUIRED`, `403 AUTH_SELLER_LINK_REQUIRED`, 인증된 요청의 CSRF 실패는 `403 AUTH_CSRF_INVALID`의 `ProblemDetail`로 반환한다. 쿠키가 없거나 무효인 변경 요청에서는 인증 실패를 우선한다. 공개 판매 목록·상세 조회와 기존 `/api/auth/me` 계약은 유지한다. 프론트엔드의 CSRF 연동 전에는 이 백엔드 전환본을 배포하지 않는다.

## 이유

요청자가 지정한 ID 헤더로 타인의 도메인 데이터를 조회하거나 변경할 수 있는 문제를 막는다. 별도 도메인 ID를 유지하면 기존 주문·배송지·상품·판매 데이터와 서비스의 소유권 검사를 재작성하지 않고도 인증 주체를 확정할 수 있다. 브라우저가 자동 전송하는 JWT 쿠키의 상태 변경 요청에는 CSRF 방어가 필요하다.

## 트레이드오프

확인되지 않은 기존 기록은 보존되지만 소유권 연결 전까지 API로 접근할 수 없다. 운영자가 외부 근거로 소유권을 검증하고 연결 데이터를 등록해야 한다. CSRF 토큰을 쿠키에 보관하므로 서버 세션 공유는 필요하지 않지만, 쿠키의 범위와 갱신·폐기 흐름을 검증해야 한다. 기존 프론트엔드는 CSRF 토큰을 전송하지 않으므로 후속 연동과 검증이 배포 선행 조건이다. 인증·CSRF 필터의 실패 순서를 통합 테스트로 유지해야 한다.
