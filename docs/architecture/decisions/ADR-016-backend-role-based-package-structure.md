# ADR-016: 백엔드 계층 내부를 역할별 하위 패키지로 구성

- 상태: 승인
- 적용 영역: backend
- 결정일: 2026-09-11

## 결정

백엔드의 각 도메인은 기존과 같이 `presentation`, `application`, `domain`, `infrastructure` 계층으로 나누고, 각 계층 내부의 클래스는 역할 또는 구체적인 책임별 하위 패키지에 둔다. 하위 패키지는 포함되는 클래스나 파일 수와 관계없이 사용하며, 단일 파일이라는 이유로 계층 패키지 바로 아래에 배치하지 않는다.

기본 역할 패키지는 다음과 같이 구성한다.

- `presentation`: `controller`, `request`, `serializer`
- `application`: `service`, `dto`, `response`
- `domain`: `model`, `repository`
- `infrastructure`: `persistence`와 외부 시스템별 `client`, `storage`, `config` 등 구체적인 책임

기본 역할로 설명하기 어려운 보조 코드는 `util`, `helper`, `common`처럼 범위가 불명확한 패키지에 두지 않고 `cursor`, `serializer`, `config`처럼 책임이 드러나는 이름을 사용한다. 실제 파일이 생길 때만 패키지를 만들며 빈 패키지를 미리 만들지 않는다.

도메인 내부에 이미지처럼 별도의 기능 경계가 필요하면 `{domain}/{layer}/{feature}/{role}` 순서로 구성한다. 이에 따라 [ADR-006](ADR-006-product-image-package-structure.md)의 상품 이미지 패키지는 `product/{layer}/image/{role}` 형태로 역할 패키지를 확장한다. 기능별 예외는 기존과 같이 `{domain}/exception`에 둔다.

테스트 코드는 대상 프로덕션 코드의 패키지를 따른다. 여러 계층을 함께 검증하는 통합 테스트는 해당 도메인 패키지에 둘 수 있다.

새로 작성하는 코드는 이 구조를 적용한다. 기존 코드의 패키지 이동은 기능 변경과 섞지 않고 별도 작업으로 수행한다.

## 이유

계층 패키지 바로 아래에 Service, Dto, Response, Repository와 보조 코드가 함께 있으면 파일 수가 늘어날수록 목록만으로 각 파일의 역할을 구분하기 어렵다. 리뷰할 때도 변경 파일의 경로가 역할을 충분히 설명하지 못해 파일 내용을 열어야 변경 범위를 파악할 수 있다.

클래스 수와 무관하게 역할별 패키지를 사용하면 파일 경로가 책임을 드러내고, 같은 역할의 코드를 일관된 위치에서 찾을 수 있다. 처음에는 단일 파일이었던 역할에 파일이 추가될 때 기존 파일을 이동하는 구조 변경도 줄어든다.

빈 패키지를 만들지 않는 원칙과 단일 파일도 역할 패키지에 두는 원칙을 분리하면, 예상 확장만을 위한 구조는 만들지 않으면서 실제 코드의 책임은 처음부터 명확하게 표현할 수 있다.

## 트레이드오프

파일 수가 적은 도메인에서도 디렉터리와 package 선언이 깊어지고, 하나의 유스케이스를 따라갈 때 여러 역할 패키지를 오가야 한다. 기능 하위 패키지와 역할 하위 패키지를 함께 사용하면 경로가 더 길어질 수 있다.

역할만으로 모든 코드를 분류하면 `util`과 유사한 모호한 패키지가 다시 생길 수 있으므로, 기본 역할에 포함되지 않는 코드는 구체적인 책임 이름을 정해야 한다. 이 과정에서 새 책임의 경계에 대한 판단이 필요하다.

기존 코드에는 대규모 package 및 import 변경이 필요하지만, 기능 변경과 분리해 수행하므로 구조 변경 자체를 독립적으로 리뷰할 수 있다.
