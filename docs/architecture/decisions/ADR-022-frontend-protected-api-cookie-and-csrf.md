# ADR-022: 보호 API의 쿠키 인증과 공통 클라이언트 CSRF 처리

- 상태: 승인
- 적용 영역: frontend
- 결정일: 2026-09-14

## 결정

구매자·판매자 보호 API는 개발용 도메인 ID 헤더 대신 로그인 사용자의 JWT 쿠키로 호출한다. 도메인 API 모듈이 보호 요청 여부를 지정하면 `shared/api/apiClient.ts`가 `credentials: 'include'`를 적용한다. 상태 변경 요청에는 `GET /api/auth/csrf`의 `{ token, headerName }`을 조회하여 서버가 지정한 이름의 헤더를 넣는다. 공개 판매 조회는 기존 공개 요청으로 유지한다.

CSRF 토큰은 페이지 메모리에만 보관한다. `/api/auth/me` 확인 후 선조회하고, 첫 변경 요청 시 토큰이 없으면 전송 전에 조회한다. 동시 변경 요청은 같은 조회 결과를 공유한다. `401 AUTH_UNAUTHENTICATED` 또는 `403 AUTH_CSRF_INVALID` 응답을 받으면 토큰을 폐기한다. 실패한 상태 변경 요청은 자동 재전송하지 않는다. 화면별 인증·연결 부재·결제 결과 판단은 각 feature의 hook에서 처리한다.

## 이유

요청 소유자를 백엔드 인증 주체로 일원화하면 프론트엔드 환경변수나 `/api/auth/me`의 사용자 ID로 도메인 ID를 추정할 필요가 없다. 쿠키와 CSRF 처리를 공통 클라이언트에 두면 도메인 API마다 토큰 처리를 반복하며 누락할 가능성을 줄이고, 기존 `features → shared` 의존성 방향을 유지한다.

## 트레이드오프

백엔드의 보호 API와 CSRF 엔드포인트 전환본이 함께 배포되어야 한다. CSRF 조회 실패 시 변경 요청을 보내지 못하며, 인증·CSRF 오류 후 사용자 재시도에는 추가 토큰 조회가 필요하다. 자동 재전송을 하지 않으므로 주문 생성과 결제 승인처럼 결과가 불확실한 요청은 화면에서 보수적으로 안내해야 한다.
