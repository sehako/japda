# ADR-025: 판매자 일일 정산과 사용자 플랫폼 지갑 원장

- 상태: 승인
- 적용 영역: backend
- 결정일: 2026-09-15

## 결정

한국 시간 기준 정산일에 승인된 결제를 구매별 정산 상세로 수집하고 판매자별·정산일별로 합산한다. 실행 시작 시 플랫폼 수수료율을 basis point로 스냅샷하고 판매자별 총 결제금액에 한 번 적용한다. 수집, 검산·확정, 지갑 입금의 3단계 Spring Batch Job을 초기에는 단일 파티션·단일 thread로 실행한다.

지갑은 판매자 전용이 아니라 `users.id`에 일대일로 귀속되는 플랫폼 공용 `Wallet`로 관리하며 최초 잔액 변경 시 멱등 생성한다. 정산은 `seller_principal_identities`로 판매자의 `userId`를 확인해 입금 대상을 스냅샷한다. 판매자별 정산 입금은 지갑 잔액 증가, 수정·삭제하지 않는 `LedgerEntry` 생성과 정산 완료 상태 전이를 하나의 DB 트랜잭션에서 수행한다.

구매별 정산 상세의 `paymentId`, 판매자별 정산의 정산 실행·판매자 조합, 원장 항목의 source 종류·source ID 조합에 각각 unique 제약을 둔다. 같은 결제와 판매자 정산을 재처리해도 중복 정산이나 중복 입금이 발생하지 않아야 한다. 데이터 오류는 skip하지 않고 Job을 실패시키며 같은 `settlementDate`의 실패한 JobInstance를 checkpoint부터 재시작한다. 업무 정산 실행에는 마지막으로 완료된 단계를 기록하고 기술적인 실패와 checkpoint는 Spring Batch 메타데이터를 기준으로 판단한다.

초기 원장은 양수 금액의 입출금 기록과 현재 잔액 projection을 관리하는 단식 원장으로 제한한다. 실제 계좌 지급, 복식부기, 취소·환불의 역분개, 정정 정산과 늦게 확정된 결제는 포함하지 않는다.

## 이유

구매별 근거와 판매자별 요약을 분리하면 어떤 결제가 정산에 포함됐는지 추적하면서 지갑에는 판매자별 합산 금액을 한 번만 입금할 수 있다. 원장 source와 결제의 데이터베이스 유일 제약은 Spring Batch checkpoint와 함께 재시작 경계가 불명확한 상황에서도 금액 중복 반영을 막는다. 입금 전 전체 검산 단계를 두면 일부 판매자만 계산된 상태에서 원장 처리를 시작하지 않는다.

지갑을 사용자에 귀속하면 한 사용자가 구매자와 판매자 역할을 함께 가져도 플랫폼 잔액을 하나로 관리할 수 있다. 원장 입금 규칙을 application 유스케이스로 모으면 배치, 향후 API와 다른 내부 실행 주체가 같은 멱등성과 트랜잭션 규칙을 재사용할 수 있다.

단일 파티션은 처리량보다 정확성, 실패 복구와 측정 기준선을 먼저 검증하기 위한 선택이다. 이후 멀티 파티션은 같은 업무 데이터와 불변식을 유지한 채 별도 성능·경합 설계로 비교한다.

## 트레이드오프

구매별 정산 상세를 영구 보존하므로 원본 결제 외에 추가 저장 공간과 쓰기 비용이 발생한다. 판매자별 합계를 여러 chunk에서 누적하므로 요약 행 갱신 비용이 있으며 향후 멀티 파티션에서는 같은 판매자에 대한 경합을 별도로 해결해야 한다. 지갑 잔액 projection과 불변 원장을 함께 저장하므로 두 값의 일관성을 같은 트랜잭션과 검증으로 유지해야 한다.

단식 원장은 플랫폼의 전체 자금 이동과 차변·대변 균형을 증명하지 못한다. 정산일을 엄격한 승인일 범위로 선택하므로 정산 완료 후 늦게 확정된 결제는 초기 범위에서 자동 처리되지 않는다. 취소·환불, 수수료 정책 변경과 실제 지급을 지원할 때 역분개, 추가 정산, 보류금과 복식부기 여부를 새로운 결정으로 기록해야 한다.
